# Feature-pipeline 复杂度分级 + 降档执行细则

> **来源**：I-1 黑名单 trial #2 复盘（CRUD 极简页跑了 ~5h / 6 次询问 / 700 行 spec / 27 条红队，全程过度工程）

## 规则

**调 feature-pipeline 前先判档**。不是所有"跨 3+ 文件 + 含状态机 + 含 UI"都走全套 7 步。

```
A 档（全量流水线 7 步）：
  接口数 ≥3，或 状态机态数 >5，或 跨 ≥1 SDK，或 含异步竞态/跨模块状态同步
  例：直播 / PK / 派对房 / 1v1 通话 / 美颜管线

B 档（精简流水线 4 步）：
  接口数 ≤2 且 状态机 ≤5 态 且 0 SDK 且 单一 view 入口
  例：黑名单 / 反馈列表 / 收益明细 / 消息列表

C 档（不走流水线）：
  单文件改动 / cosmetic 调整 / bug 修复
```

**判定要求**：阈值用 **spec 起草前可判断的硬指标**（接口数 / 状态机态数 / SDK 数），不用 "反向用例数 R-*"（需要先写 spec 才能数，是循环依赖）。

## Why

trial #2（I-1 黑名单）是典型 B 档（2 接口 / 4 状态 / 0 SDK），被错误按 A 档执行：
- 实际用时 ~5h vs 期望 ~1h（**5×**）
- 6 次询问全部"推荐默认"——这些是**确认点伪装成决策点**
- spec 699 行 vs 期望 ~150 行（**4.6×**）—— trial #1 模板被机械复制
- Plan agent red team 27 条意见，其中 17 接受多为 token 化/a11y 微调，5 critical 即可

错误归因不是"skill 触发条件设计不好"，是**执行者（我）没有判断力主动降档**——看到"跨 3 文件+状态机+UI"就 yolo 全跑。

## How to apply

### B 档降档执行细则（必须照做）

| 维度 | A 档（默认） | B 档（降档） |
|---|---|---|
| **step 拆分** | 0/1a/1b/1c/2/3/4/5/6 共 9 步 | 0 / impl（合并 1a+1b+1c+2）/ 真集成+真机 / 5（轻量）/ 6（事件触发） |
| **询问** | step 0 多次 picker 中断 | **确认点用陈述+反驳指引**（"我按 X 推进，如非此意请打断"），**决策点才用 AskUserQuestion** |
| **spec 篇幅** | 12 节 + 附录（700 行）| **5 节（150 行）**：业务+契约 / model+状态机 / 验收(F 全列 + R critical 3-5 条) / 复用判断 / 待问用户(仅 critical) |
| **red team** | 全方位评审，27+ 条意见 | **提示词改目标"只挖 spec 未覆盖的 case，不报品味优化"**（待先 Read 现状 prompt 后改） |
| **TodoWrite** | 每 step 切换更新 | **禁用**（单线程流程用 todo 是仪式化） |
| **xcodebuild test** | 每验收门跑一次 | **无改动不跑**（仪式化测试是隐藏成本） |
| **step 3 / 4** | 拆 2 步 | **合并**为「真集成+真机签字」单步 |
| **step 6** | 强制做 | **反悔 0 → 跳过**；反悔 ≥1 → 必做 |
| **sink rule** | step 6 仪式化沉淀 | **新 rule 与本次 checklist 重复 ≥50% → 不沉淀**（见 `docs/plan/废弃-feature-pipeline零反悔自检-*.md` 元教训） |

### 维度匹配（用户痛点 → 治本建议）

**"询问太多" ≠ "流程太长"**，分维度治：

- **治中断成本**：上表「询问」「TodoWrite」行 → 6 次 picker → 1 次文档反馈
- **治总耗时**：上表「step 拆分」「spec 篇幅」「step 3+4 合并」「step 6 事件触发」行
- **治评审噪声**：上表「red team」行，间接减总耗时

### 自检清单（B 档执行中实时核对）

进入流水线前问自己：

- [ ] 是否符合 B 档阈值（接口数 ≤2 + 状态机 ≤5 态 + 0 SDK + 单一入口）？
- [ ] 即将用 AskUserQuestion 的点，是真决策还是确认？若是确认 → 改陈述+反驳
- [ ] spec 草稿超过 200 行？→ 砍元节（§0.3 信源限制 / §8 rules 候选 / §11 自检 / §12 红队详细落地都不应进 spec）
- [ ] red team 输出 ≥10 条？→ 重写提示词限定"挖未知 case"
- [ ] 当前 step 是否真有改动需要测试？无 → 跳过 xcodebuild test

## 不适用场景

- **A 档任务**：仍按全量 7 步，本规则不降档
- **C 档任务**（单文件 bug 修复）：本来就不走流水线，本规则无关
- **首次试某新形态功能**：即使硬指标命中 B 档，若是项目内首次尝试该形态（如首次做"无限滚动"、首次做"WebSocket 列表"），可一次性按 A 档跑作为投资 — **明示决定**，不能默认 A 档

## 与既有规则关联

- **不与 `feature-pipeline` skill 冲突**：skill 是"做什么 + 怎么做"，本规则是"什么时候不做这么多"。skill 已写"何时不调用"（C 档），本规则补"调用了如何降档"（B 档）
- **不与 `async-state-fallback.md` 冲突**：那条代码级；本条流程级
- **延续 `docs/plan/废弃-feature-pipeline零反悔自检-*.md` 元教训**：仪式化沉淀反模式

## 复查收敛标准（避免本规则被滥用做无限优化）

本规则诞生于"三次复查直至终版" 的复盘过程。**复查应在"产出从重写降到微调矛盾"时收敛**——再复查就是完美主义 retro，与流程过长是同根反模式。

→ 本规则**不要再扩展**。下次想加新维度时，先问"是不是又在仪式化"。
