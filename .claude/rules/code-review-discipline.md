# 代码审查与修复纪律

## 1. 发现问题先评估实际触发场景

复查发现的"问题"必须先评估**实际产品调用链路上能否真触发**——不以代码风格为标准。

- 找具体触发场景：什么操作 / 什么时序
- 找产品调用证据：grep 实际调用方
- 找不到具体路径 → 降级为"建议"

## 2. 分级建议

| 分级 | 标准 |
|---|---|
| **必修** | 有产品调用链路证据 + 真影响功能 / 提审 / 安全 |
| **建议** | 无具体触发证据；代码角度有改进空间；**或**品味洁癖但符合 §9 例外（有可量化性能增益或具体安全增益） |
| **信息** | 纯风格 / 洁癖 且不符合 §9 例外 |

## 3. 禁止私自修改

复查模式下任何代码改动都需用户明确批准：

- 批准范围 = 用户明确说的（"修 P0+P1"、"全修"、"修第 X 项"）
- 批准范围**外**的改动——「顺手做」「明显的 fix」「改造时一起做了」——都是反模式
- 改造引入的回归 / 暴露的 pre-existing bug——先列报告等用户决策

## 4. 改造完成后主动评估副作用

改造完成后必须主动评估**引入**或**暴露**的 bug，列给用户,不私自修。

## 5. Finding 报告格式

```
- 标题：一句话
- 文件：file:line
- 触发场景 + 概率：什么调用链路；实际产品中会发生吗
- 严重度：阻塞 / 中 / 低
- 建议：必修 / 建议 / 信息
```

## 6. 常见误判 bug 类型

| 误判 | 现实 |
|---|---|
| "看代码不优雅" | 不是 bug，是建议；**若符合 §9 例外（性能/安全增益）→ 升级为建议级** |
| "理论上时序可能" | 找产品调用链路证据，找不到降级 |
| "防御性加固" | 先证明"不加固会出问题"，不能证明降级 |

## 7. 工具产出 ≠ 二次复查

任何自动化工具（Workflow / Agent / linter / 静态分析）输出的 finding，**都只是 finder 阶段结论**，等同于规则 §1 的初次判定，**不**能替代二次复查：

| 工具内置机制 | 是否等同二次复查 |
|---|---|
| Workflow 内 3 票对抗（correctness / severity / fix-validity）| ❌ —— 投票 agent 也是基于 prompt 推理，没真 grep 调用方 |
| Agent 自我"已确认" | ❌ —— agent 看不到产品全局调用链 |
| Static analyzer 标红 | ❌ —— 不区分理论问题 / 实际触发 |
| LLM 评分 ≥9 | ❌ —— 评分是输出质量，不是事实校验 |

**必须自己做**：Read 涉及文件对应行号 + Grep 实际调用方 + 按 §1/§2/§6 分档。

### 适用场景
- `/review deep` 跑完 Workflow 后渲染报告之前
- 任何 Agent 调用返回 finding 列表之前
- 私有/外部 linter 输出 issue 列表之前

## 8. 历史教训

H 里程碑 IM 审查中私自改 6 项：含真 bug（CallStore HUD 残留、callElapsed `.connecting` 杂值）、理论 bug 不触发（hasJoined 时机、NIMOnlineKeeper 时序）、边际优化（BeautyPanel onDisappear sync）、连锁防御（rollbackEnterFailure）。

**无论 bug 严重度，未经用户批准就是私自修改**。

I 期 IM `/review deep` 跑完 Workflow（59 agents / 3 票对抗）后直接渲染 11 项报告，跳过自己二次复查 → 用户指出 2 项 finder 误判 + 4 项理论不触发的标错严重度。教训：**Workflow 内对抗票 ≠ 规则要求的产品调用链证据**，§7 沉淀。

v5.5 空闲清理审查（4 文件小范围）：Workflow 5 finder 全 stalled 烧 2.59M tokens 无产出 + 手工首轮列 6 条 P1/P2、用户第 3 轮筛除 4 条防御性洁癖（错解 SDK 顺序 / 未测预优化 / weak self 单例 / 服务端配置无解）。**新准则**：**Review 找"该改的"不是"能改的"**——理论存在 + 0 触发证据 + 修复是防御性 = 剔除；小范围审查（≤10 文件）跳 Workflow 直接手工更高效。

## 9. 品味洁癖的例外：性能/安全增益值得采纳

§2 把"品味/洁癖"归"信息"级剔除，但命中以下**具体证据**任一 → 升级为建议级采纳：

- **性能可量化**：网络请求数减少 / 内存 CPU 消耗降低（Instruments 数据）/ 首帧或冷启延迟缩短 / 数据结构复杂度改善
- **安全增益具体**：类型安全（编译期防 typo/漏 0）/ 内存安全（引用循环、悬垂）/ 并发安全（actor / Sendable / data race）/ 输入验证 / crash 兜底

**判定纪律**：引本例外时必须**明示具体增益点**（如"漏 0 手误 → runtime bug"），不能泛泛说"类型/性能更好"，避免把 nitpick 强行包装升级。

**正例**（采纳）：
- `Task.sleep(nanoseconds: 300_000_000)` → `Task.sleep(for: .milliseconds(300))`：`Duration` 类型防漏 0 手误
- `try! decode(...)` → `try? ... ?? default`：crash 兜底
- 循环 `array[i]` → `for-in`：索引越界防护

**反例**（仍剔除）：
- "更 idiomatic" / "for future-proof" —— 无量化增益
- 新旧 API 行为等价且旧未 deprecated —— 如 iOS 15 前 `foregroundColor` vs `foregroundStyle`
- 单独改一处破坏项目主流风格一致性
