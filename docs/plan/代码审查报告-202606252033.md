## 二、P0（必须改）

### P0-1 pushFrame 在 videoQueue 读取 @MainActor 写入的 engine / state / videoSeatActive — 数据竞争

- **文件**：[PartyRTCEngine.swift:281-288](Sources/Party/RTC/PartyRTCEngine.swift#L281-L288)
- **维度**：Swift 并发
- **风险**：`pushFrame` 是 `nonisolated` 方法（无 `@MainActor` 注解），由 `CameraManager.captureOutput` 在 videoQueue 后台串行调用；但函数体内读取 `engine`（`private var`、@MainActor 写）、`state`（`@Published`、@MainActor 写）、`videoSeatActive`（`private(set) var`、@MainActor 写）这三个 mutable 字段。`upperSeat / enableVideoSeat / leave` 等 @MainActor 方法重写这些字段时与 videoQueue 的读发生数据竞争：在 `leave()` 期间将 `engine` 置 nil 的瞬间，captureOutput 可能拿到半状态指针调 `pushExternalVideoFrame` → 崩溃或下发到已销毁实例。Swift 6 严格并发会直接编译失败；当前 Swift 5 默认 mode 静默通过但仍是 UB。**与 CLAUDE.md v5.3.1「CIImage / CVPixelBuffer 跨线程 ARC 不安全」同源问题**。
- **修复**：思路 A（推荐，与 CameraManager 现有锁模式一致）—— 把 pushFrame 体内访问的字段抽到原子快照（NSLock + 局部结构体）：

  ```swift
  private let frameLock = NSLock()
  private var frameSnapshot: (engine: AgoraRtcEngineKit?, active: Bool)?
  @MainActor private func updateFrameSnapshot() {
      frameLock.lock(); defer { frameLock.unlock() }
      frameSnapshot = (engine, state == .joined && videoSeatActive)
  }
  func pushFrame(_ pb: CVPixelBuffer) {
      frameLock.lock(); let snap = frameSnapshot; frameLock.unlock()
      guard let kit = snap?.engine, snap?.active == true else { return }
      // ... AgoraVideoFrame 推送
  }
  ```

  在 `enableVideoSeat` / `disableVideoSeatInternal` / `leave` / 收到 `didJoinChannel` 时调 `updateFrameSnapshot`。

  思路 B（简化）：把 engine/active 状态合并成单个 nonisolated AtomicReference 类，pushFrame 直接读 atomic。生产推荐 A。

## 三、P1（应该改）

### P1-1 1012 信令把整个 remoteExt 标 .public 打印 → PII 泄露

- **文件**：[PartyMessageRouter.swift:76](Sources/Party/NIM/PartyMessageRouter.swift#L76)
- **维度**：安全与隐私
- **风险**：`case .seatUpdateList` 时 `AppLogger.party.notice("...1012 ext=\(ext, privacy: .public)")` 把整个 NIM remoteExt 字典以 `.public` 输出到 OSLog。`ext` 来自服务端聊天室广播的麦位变更通知，至少含 attachType + data 字段，data 解压后可能含全量 seatList（userId / nickname / avatar / yxAccid / roomRoleType 等 PII）。生产包 OSLog 默认会持久化到设备日志，可被串流工具与 Sysdiagnose 拷贝。
  与 [PartyMessageRouter.swift:118/122](Sources/Party/NIM/PartyMessageRouter.swift#L118) 的 kickedOut 路径使用 `.private` 处理 roomId/userId 形成**自相矛盾**——同一类业务字段在不同分支保护级别不一致，明显是临时调试日志漏改。
  spec §1.5 #5 与 [PartyStore.swift:563](Sources/Party/PartyStore.swift) 已明确 payload schema 仍待 implement 期抓真实帧，说明这条 ext 日志原本是 dev 期调试目的；**上线前必须降级**。
- **修复**：改为只输出非 PII 元数据：

  ```swift
  case .seatUpdateList:
      AppLogger.party.notice("[PartyRouter] 1012 keys=\(Array(ext.keys), privacy: .public)")
      delegate?.partyRoomChatDidRequireSeatListReload(chat)
  ```

  若调试期仍需查 ext 内容，改 `.private` 让生产环境自动脱敏。

### P1-2 PartyStore.enableLocalVideoCapture sink 闭包引用 rtc 但跨 actor — 潜在数据竞争

- **文件**：[PartyStore.swift:480-492](Sources/Party/PartyStore.swift#L480-L492)
- **维度**：Swift 并发
- **风险**：subscribe 的 sink 闭包 `capture let rtcRef = rtc`，闭包执行在 CameraManager.videoQueue 调 `rtcRef.pushFrame()`——这条调用链落到 P0-1：pushFrame nonisolated 读 @MainActor mutable 字段。**即使本闭包语义正确，本质上是把 PartyRTCEngine 的 actor isolation 漏洞暴露给 PartyStore**。下麦/退房时 PartyStore.disableLocalVideoCapture 在 @MainActor 调 unsubscribe，但 captureOutput 可能正在调 rtcRef.pushFrame——unsubscribe 删 sink 后该次调用已 in-flight，pushFrame 内 `guard let engine` 不可靠（非原子）。
- **修复**：随 P0-1 修复同步（pushFrame 加 NSLock + snapshot 后这里无需改）；或退房路径加 200ms grace 让 sink 退避（与 v5.8 设计同精神）。

### P1-3 PartyStore 巨型 ObservableObject 引发失效风暴

- **文件**：[PartyStore.swift:15-47](Sources/Party/PartyStore.swift#L15-L47)
- **维度**：SwiftUI 性能
- **风险**：PartyStore 同时持有 **11 个 @Published 字段**（roomInfo / seatList / onlineUserCount / isJoinedChannel / imAlive / lastGiftEvent / roomState / pendingVideoSeatInvite / lastInviteResult / lastError / isLocalCameraActive）。PartyRoomView 用 `@ObservedObject` 全量观测，且 9-12 个 PartySeatItemView 也都用 `@ObservedObject` 观测同一个 store。任何一个字段变化 → 整页 + 全部 seat cell 同时 re-render，连带 PartyRemoteVideoView / CameraPreview 反复触发 SwiftUI re-eval，**加大相机预览/远端视频抖动风险**（与 `swiftui-camera-preview.md §2` 鲁棒前提相悖）。E MVP 麦位数不大未必崩，F 期视频位/礼物动画/邀请提示频繁后必现卡顿。
- **修复**：拆 store 为多个细粒度 ObservableObject：
  - `PartyRoomSeatStore`（seatList / onlineUserCount / isLocalCameraActive）
  - `PartyRoomLifecycleStore`（roomState / isJoinedChannel / imAlive / lastError）
  - `PartyRoomFeedStore`（lastGiftEvent / pendingVideoSeatInvite / lastInviteResult）

  **最小改**：PartySeatItemView 把 `@ObservedObject var store` 改为 `let isLocalCameraActive: Bool` + `let camera: CameraManager?` 参数，父 view 提取后下发——从源头切断每 seat cell 跟所有 @Published 字段的耦合（同 P1-8）。

### P1-4 AgoraRtcEngineDelegate 回调 Task 闭包未用 weak self

- **文件**：[PartyRTCEngine.swift:343-394](Sources/Party/RTC/PartyRTCEngine.swift#L343-L394)
- **维度**：Swift 并发
- **风险**：`rtcEngine(_:didJoinChannel:...)` / `didJoinedOfUid` / `didOfflineOfUid` / `didOccurError` / `connectionChangedTo` 等 **5 处** `Task { @MainActor in self.xxx = ... }` 均缺 `[weak self]`。Agora SDK 回调来自 SDK 内部线程，hop 到 @MainActor 期间 Task 持 strong self；若用户连续多次进退派对房 + 网络抖动产生大量 connection state 回调，Task 队列 backlog 会强引用旧 PartyRTCEngine 实例延迟到队列消化完才释放。**与 D v5.3.2「声网 SDK 后台 backlog 一次性串行触发 forceEnd」是同类问题**。`didLeaveChannelWith` 已经用了 `[weak self]`，明显是漏写。
- **修复**：5 处全部改为：

  ```swift
  Task { @MainActor [weak self] in
      guard let self else { return }
      // ...
  }
  ```

### P1-5 ForEach(sortedSeats, id: \.id) 中 id 为 Optional<String> — Identity 坍缩

- **文件**：[PartyRoomView.swift:170, 178-180](Sources/Party/UI/PartyRoomView.swift#L170)
- **维度**：SwiftUI 性能
- **风险**：`PartyRoomSeat.id` 是 `String?`（[PartyRoomSeat.swift:24](Sources/Party/Models/PartyRoomSeat.swift#L24) 注释「数据库 ID，非业务」），dev 后端某些场景可能返 nil 或缺该字段。一旦多麦位的 id 同时为 nil，ForEach 收到多个 `Optional.none` 作为 Identity key → SwiftUI 控制台 warning + 视图复用混乱。**最直接后果**：PartyRemoteVideoView 的 `makeUIView` 被 SwiftUI 误调用多次（同 seatIndex 多次 acquireRemoteView 仍返同实例所以不丢首帧，但 `dismantleUIView` 会被乱触发导致 `canvas.view = nil` → **远端视频黑屏**）。违反 `swiftui-camera-preview.md §2`「UIViewRepresentable 包装的强持有 UIView 单例禁止反复 makeUIView」。
- **修复**：ForEach 改用稳定业务键 seatIndex：

  ```swift
  ForEach(sortedSeats, id: \.seatIndex)
  ```

  同步把 [PartyRoomListView.swift:63](Sources/Party/UI/PartyRoomListView.swift#L63) 的 `id: \.id` 也改为稳定字段。

### P1-6 PartyRoomView 同时观测 store 与 chat — 公屏高频驱动整页 re-render

- **文件**：[PartyRoomView.swift:25-26, 116, 207, 224](Sources/Party/UI/PartyRoomView.swift#L25)
- **维度**：SwiftUI 性能
- **风险**：PartyRoomView 顶层 `@ObservedObject` 同时挂 store + chat。`chat.messages` 每收一条 NIM 公屏消息（房间活跃时 >5 条/秒可能）→ 触发 PartyRoomView 整 body 重算 → seatGrid（含 PartyRemoteVideoView / CameraPreview）整组重 evaluate。`chat.onlineCount` 每个用户 enter/exit 通知都 +/- 一次（line 247）也会引发同等失效。在大房间或频繁发言时，麦位区/视频位画面被 SwiftUI 反复 dismantle/init 包裹层。**配合 P1-5 的 id Optional 风险，远端首帧丢失 + 本端摄像头闪烁的概率显著上升**。
- **修复**：把公屏区抽成独立子视图 `PartyMessageListView(chat: chat)`，让 chat 仅被该子视图观测；PartyRoomView 不直接挂 `@ObservedObject var chat`。同理把 header 内 `chat.onlineCount` 抽到 `PartyHeaderView(chat: chat, store: store)` 子视图。

### P1-7 PartySeatItemView 麦位角标 .offset 硬编 ±22 不随 RTL 镜像

- **文件**：[PartySeatItemView.swift:50, 54](Sources/Party/UI/PartySeatItemView.swift#L50)
- **维度**：iOS 平台规范
- **风险**：工程已声明 ar/tr 三语言（CLAUDE.md 明确要求布局用 leading/trailing 而非 left/right 自动镜像）。麦位角标用 `.offset(x: -22, y: -22)` 把序号固定到左上、麦克风状态 icon 固定到右下，是绝对 x 偏移——SwiftUI **不会按 RTL 翻转 .offset**；阿语用户看到的麦位编号、mic 状态会跑到与 H5/安卓相反的角落，与对方互动状态认知错位（视觉错位也会被 App Store 审核员当 RTL 缺陷打回）。
- **修复**：把角标放到 ZStack 的 `.topLeading` / `.bottomTrailing` alignment 容器里，让 SwiftUI 自动按布局方向镜像；或者按 `@Environment(\.layoutDirection) == .rightToLeft` 反转 x 符号；偏移量改成 `.padding(-8)` 或 `.alignmentGuide` 也行——**不要继续用裸 `.offset(x:)`**。

### P1-8 PartySeatItemView 每个 cell 都挂 @ObservedObject var store: PartyStore

- **文件**：[PartySeatItemView.swift:14, 25, 58](Sources/Party/UI/PartySeatItemView.swift#L14)
- **维度**：SwiftUI 性能
- **风险**：每张麦位卡片都 `@ObservedObject` 同一个 PartyStore。9-12 个 cell × 11 个 @Published 字段 → 任意字段变化全部 cell 一起 re-render。具体后果：`lastGiftEvent` 收到一次礼物（视图层不显示但 store 字段确实变）就会让 9 张麦位卡同时重算，包括 PartyRemoteVideoView 的 struct 重新构造 + CameraPreview 重 evaluate。CameraPreview 现有 v5.8 Coordinator 模型能扛，但 SwiftUI re-eval 频率从「seat 变」变成「任意 store 字段变」，**浪费 main thread 时间并放大任何潜在 identity 漂移风险**。
- **修复**：PartySeatItemView 不观测 store，所需字段全部从父视图参数传入：

  ```swift
  struct PartySeatItemView: View {
      let seat: PartyRoomSeat
      let isSelf: Bool
      let isLocalCameraActive: Bool       // 替代 store.isLocalCameraActive
      let camera: CameraManager?           // 替代 store.camera
      let engine: PartyRTCEngine           // 替代 store.rtc
  }
  ```

  父 view 在 seatGrid 里从 store 提取后传入。这样 seat cell 仅当 seat 结构本身变（ForEach diff 命中）时 re-render。

### P2-5 PartyStore 失败回调调 lastError 在 Task 之外 — 状态时序覆盖

### P2-8 PartyRTCEngine / PartyRoomChatManager 缺 deinit 兜底

- **文件**：[PartyRTCEngine.swift:25-67](Sources/Party/RTC/PartyRTCEngine.swift#L25-L67)；同类问题 [PartyRoomChatManager.swift:33](Sources/Party/Chat/PartyRoomChatManager.swift#L33)
- **维度**：内存与资源
- **风险**：PartyRTCEngine 没有 deinit；当前靠 `PartyStore.shared` app 级单例 + 显式 leave 路径补清，但一旦未来拆不是单例或 leave 未走完走销毁路径，`sharedEngine.delegate` / `NIMSDK.chatManager` / `chatroomManager` 会指向已释放实例。Agora delegate 是 weak 不崩但 setExternalVideoSource / setChannelProfile 等状态无回滚，会污染下一场景；NIMSDK delegate 未 remove 可累积多个残留实例争抢同一套回调。
- **修复**：

  ```swift
  // PartyRTCEngine
  deinit { if engine?.delegate === self { engine?.delegate = nil } }

  // PartyRoomChatManager
  deinit {
      NIMSDK.shared().chatManager.remove(self)
      NIMSDK.shared().chatroomManager.remove(self)
  }
  ```

  deinit 不发起 async leaveChannel/exitChatroom（无法在 deinit 中 await），只做 delegate 解绑。

### P2-9 releaseAllRemoteViews for-in 中 mutate 所迭代字典

- **文件**：[PartyRTCEngine.swift:271-278](Sources/Party/RTC/PartyRTCEngine.swift#L271-L278)
- **维度**：内存与资源
- **风险**：`for (seatIndex, _) in seatIndexToBoundUid` 循环体内调 unbindRemoteVideo 会在 line 265 写 `seatIndexToBoundUid[seatIndex] = 0`。Swift Dictionary COW 使当前代码必如人意迭代完所有 key，但**在循环中 mutation 被迭代容器是 Swift 明令未定义行为**；任何后续 SDK 升级把 setupRemoteVideo 改成异步回调写入该字典就会真崩，隐藏调试成本高。
- **修复**：快照 keys 再迭代：

  ```swift
  for seatIndex in Array(seatIndexToBoundUid.keys) {
      unbindRemoteVideo(seatIndex: seatIndex)
  }
  ```

### P2-10 sortedSeats 是 body 内 computed property，每次重算全量 sort

- **文件**：[PartyRoomView.swift:178-180](Sources/Party/UI/PartyRoomView.swift#L178-L180)
- **维度**：SwiftUI 性能
- **风险**：sortedSeats 在每次 body 重算都执行一次 O(n log n) 排序 + 数组拷贝。E MVP 9-12 个麦位影响不大，但**配合 P1-6（chat 高频驱动 body 重算）相当于每条公屏消息都触发一次排序**。F 期房间模板上限拉高 + 礼物广播 + 房态信令并发时，可能进入感知范围。
- **修复**：把排序收敛到 PartyStore 内部（seatList 在写入时即按 seatIndex 排序），UI 直接用 `store.seatList`；或者在 PartyRoomView 里用 `@State` + onChange 缓存：

  ```swift
  @State private var sortedSeats: [PartyRoomSeat] = []
  .onChange(of: store.seatList) { new in
      sortedSeats = new.sorted { ($0.seatIndex ?? 0) < ($1.seatIndex ?? 0) }
  }
  ```

### P2-11 messageList LazyVStack 把 gift 行混入 chat.messages ForEach 末尾

- **文件**：[PartyRoomView.swift:203-228](Sources/Party/UI/PartyRoomView.swift#L203-L228)
- **维度**：SwiftUI 性能
- **风险**：LazyVStack 内一边 `ForEach(chat.messages)` 一边在末尾插 `if let g = store.lastGiftEvent`。store.lastGiftEvent 来自全局 store，每次收礼 → LazyVStack body 重算 + onChange(of: chat.messages.count) 不一定触发但 ForEach 的元素 + gift 行的相对位置变化会让 LazyVStack 重新 diff。**叠加 P1-3 / P1-6 后，礼物事件影响公屏列表稳定性**。视觉上不直接坏，但增加 scroll-to-bottom 误触发风险。
- **修复**：把 gift 行从 LazyVStack 内剥离，要么放到 ScrollView 外覆盖层，要么把 gift 也归并进 `chat.messages` 数据流（用 PartyChatMessage 的 `.gift` msgType 承载）。同时 onChange 改监听 `chat.messages.last?.id` 而非 count，避免礼物事件不滚但 count 不变时漏滚。

### P2-12 PartyRoomView seatIndex / nickname / micIndicator 缺少 accessibilityLabel

- **文件**：[PartySeatItemView.swift:44, 93-102](Sources/Party/UI/PartySeatItemView.swift#L44)
- **维度**：iOS 平台规范
- **风险**：麦位编号渲染为孤立 `Text("\(seat.seatIndex ?? 0)")`，micIndicator 用 `mic.fill` / `mic.slash.fill` SF Symbol 不带 accessibilityLabel；**VoiceOver 读出来分别是"1" / "Microphone"——盲人用户分不清是 1 号麦位还是 1 个用户，无法判断麦位是否被禁麦**。Apple HIG 明确要求纯图形状态指示器必带 accessibilityLabel。PartyRoomView header 的 xmark.circle.fill 退房按钮（line 128）、PartyCreateRoomView checkmark.circle.fill（line 56）同此类——等 4 处。
- **修复**：

  ```swift
  Image(systemName: sysName)
      .accessibilityLabel(micOn ? L10n.Party.accessibilityMicOn : L10n.Party.accessibilityMicOff)
  ```

  退房按钮加 `.accessibilityLabel(L10n.Party.leaveRoom)`；seatIndex 角标 `.accessibilityLabel(String(format: L10n.Party.seatNumberFormat, idx))`。

### P2-13 PartySeatItemView 全用 .font(.system(size:)) 固定字号不支持 Dynamic Type

- **文件**：[PartySeatItemView.swift:40, 45, 66, 98](Sources/Party/UI/PartySeatItemView.swift#L40)
- **维度**：iOS 平台规范
- **风险**：PartySeatItemView / PartyRoomView / PartyRoomListView / PartyCreateRoomView 公屏文本、昵称、占位 icon 全部 `.font(.system(size: 10~22))`（Party 模块共 **16 处硬编码 size**），用户调大字号（无障碍设置 Dynamic Type accessibility sizes）不会缩放；视障 / 老年用户在大字号档下看到的派对房文字仍是 11pt——不满足 HIG 无障碍要求，**提审会被审核员标记 "does not support Dynamic Type"**。
- **修复**：改用语义字号 `.font(.caption2) / .caption / .footnote / .body / .title3`，让 SwiftUI 自动跟随用户偏好；确实需要固定 size 时用 `.dynamicTypeSize(.small ... .accessibility3)` 显式声明上下限。

## 六、横切观察 / 系统级建议

1. **PartyStore 拆分是后续 F 期最大的架构债**——P1-3 / P1-6 / P1-8 / P2-10 / P2-11 五条都指向同一问题：单一全量 ObservableObject 是 SwiftUI 性能反模式。建议 F 期开工前先做拆 store 重构（3 个细粒度 store + PartySeatItemView 去 @ObservedObject）。
2. **声网 RTC 的并发模型需要统一原则**——P0-1 / P1-2 / P1-4 / P2-7 / P2-8 五条都指向 PartyRTCEngine 与 main actor / SDK 后台线程的交互不一致。建议沉淀一条 `.claude/rules/agora-actor-isolation.md`：明确「nonisolated 入口（pushFrame）必须用锁守 mutable 状态 + SDK delegate 回调统一加 weak self + deinit 解绑 delegate」三条铁律。
3. **日志隐私分级缺统一规则**——P1-1 / P2-2 / P2-3 / P2-6 四条都是隐私级别标注问题。建议沉淀 `.claude/rules/oslog-privacy.md`：业务 trace ID（roomId / channelId / liveId）= `.public`，用户 PII（userId / accid / nickname / token）= `.private`，原始 payload / raw response = `.sensitive` 或 `#if DEBUG`。
4. **RTL + Dynamic Type 应作 F 期视频位 UI 重构的入口检查项**——P1-7 / P2-12 / P2-13 都是国际化 + 无障碍硬伤，App Store 审核风险。
