# Web vs 安卓 主播端 业务差异分析

> **需求** DM-20260616-004 原生iOS主播端 · **阶段三交付物**(对应需求步骤3)
> **依据**:阶段一《功能概览与差异速览》+ 阶段二 12 个业务域深度梳理文档(`02-01`~`02-12`)
> **目的**:整理 Web(h5-anchor)与安卓(android-anchor)两端完整业务功能的**差异点**,并给出 **iOS 端取舍建议与工作量分级**,作为原生 iOS 主播端立项的功能规格基线。

---

## 1. 差异分析方法

差异分为四类,后文统一用此分类标注:
- **【缺失】功能缺失**:一端有、另一端完全没有。
- **【交互】交互/形态不同**:都有该功能,但页面边界、操作路径、展示形态不同。
- **【规则】业务规则不同**:都有该功能,但阈值/频率/算法/状态码等业务参数不同。
- **【平台】平台能力限制**:差异源于 Web/原生平台本身能力(如保活、推流栈),非业务设计差异。

iOS 取舍基准用三档表示:**以安卓为准** / **以 Web 为准** / **需产品决策**。

### 3.3 ⚠️ 双端有但差异显著

**【交互】交互/形态不同**
- **直播间页面边界**:Web 开播配置+直播间同页(`liveSetting` v-if 切换);安卓拆 `LiveSettingActivity`+`LiveCallActivity` 两个独立页。→ **iOS 以安卓为准**(边界清晰)。
- **1v1 通话形态**:Web 全局浮层(`g-waitingCall`/`g-remote-pip`)无独立路由;安卓独立 `ShengWang1V1CallActivity`。→ **iOS 以安卓为准**。
- **审核态降级**:Web 降级"页面"(`mineRestricted`/`newsRestricted`,SPA 路由分流);安卓独立"审核态壳"(`AuditStatusMainActivity` 双 Tab+专用 WebSocket)。→ **iOS 以安卓为准**(独立壳)。
- **等级面板**:Web 在 `dataStatistics` 单页集中(好评率+三指标升降级+权益+扣分);安卓分散到多页且升降级/权益接口未调。→ **iOS 以 Web 为准**(集中面板更完整)。
- **任务拆分粒度**:Web 细(task/dailyTask/newBie/work 四套页);安卓粗(统一容器+直播间三弹窗)。→ iOS 任一,建议适度合并。

**【规则】业务规则不同**
- **直播心跳频率**:Web 6 秒/失败>6 次下播;安卓 10 秒/失败>3 次下播。→ **iOS 需与后端确认统一值**(建议对齐安卓 10 秒)。
- **弱网强制下播阈值**:Web 连续 30 次极差;安卓连续 10 次。→ 需后端确认。
- **收款通道**:Web 三通道(USDT/Epay/Digifinex);安卓仅 USDT/Epay(其余已注释)。→ **iOS 首版对齐安卓**,Digifinex 视配置。
- **自定义附件枚举**:Web attachType 散落 if 判断;安卓集中 `CustomAttachmentType` 枚举(类型安全)。注意代充 `AGENT_RECHARGE_NOTIFY=151`(安卓 int)vs H5 `99` 的语义映射。→ **iOS 以安卓枚举为准**,严格对齐两种附件结构(`{type,data}` 数字型 + 顶层 `attachType` 字符串型)。
- **密码加密**:两端均 `MD5(密码+AppId)` 两次+转大写(刻意对齐)。→ **iOS 必须复刻**,否则跨端账号互通失败。

**【平台】平台能力限制**
- **RTC 栈**:Web Agora 单栈;安卓 Agora(主)+NERTC(备,疑似退役)。→ iOS 声网单栈。
- **美颜 SDK**:Web NamaSDK(FaceUnity Web 版)+ 浏览器 canvas 管线;安卓 FaceUnity 原生 + Agora 自定义采集帧级读写。→ **iOS 集成 FaceUnity iOS SDK**,对标安卓而非 Web。
- **保活**:Web 靠 `visibilitychange`;安卓前台 `StayService`。→ iOS PushKit+CallKit。
- **路由守卫**:Web 无 `beforeEach`(已注释),`App.vue` checkLogin 兜底;安卓 `WelcomeActivity` 单点判定。

## 5. iOS 端取舍建议

### 5.1 总原则
**以安卓为主要基准**:安卓是原生端,页面边界、状态机、SDK 集成方式与 iOS 最接近,且功能最全(派对房、进阶美颜、亲密度、计费定价均以安卓为唯一/完整来源)。Web 在少数集中式页面(等级面板、大R)设计更优,可择优借鉴。后端接口三端共用,iOS 无需后端大改。

### 5.2 分期建议(按工作量与优先级)

**第一期(MVP,核心接单闭环)** — 对应 T0+部分 T1:
账号(登录/审核态/人脸)→ 直播核心(开播/直播间/下播)→ 1v1通话(声网 CallApi+计费)→ IM/聊天 → 钱包/提现 → 工作台/在线时长 → 首页框架。
这是"主播能登录、能开播、能接单赚钱、能提现"的最小闭环。

**第二期(完整运营)** — T1 剩余+T2:
直播PK → 任务/成长 → 数据/排行榜(+大R)→ 美颜(FaceUnity 基础+进阶)→ 社交/内容(圈子/关注/亲密度/邀请)→ 设置/资料完善。

**第三期(增值,需产品决策)** — T0 派对房 + 长尾:
派对房(XL,建议再拆 MVP/完整两步)→ 短视频 → 代理/公会 → 转盘 → 其他运营玩法。

### 5.3 平台特性必须重写项(安卓→iOS)
1. **保活/来电**:StayService → **PushKit(VoIP Push)+ CallKit**,后台音视频靠 `UIBackgroundModes`(audio/voip)。
2. **登录**:补 **Sign in with Apple**(后端 `iosLogin` 已就绪),保留邮箱密码(复刻加密)。
3. **深链**:`anchorapp://` → URL Scheme + **Universal Links**;Adjust iOS SDK;自建统一 deeplink router(安卓未在 Welcome 显式解析)。
4. **版本更新**:**禁止外部浏览器下载**,强更只能跳 App Store。
5. **在线时长**:iOS 后台定时器不可靠,用**进入后台时间戳差值补算**而非持续 timer。
6. **美颜**:FaceUnity iOS SDK + `AgoraVideoFrameDelegate` 自定义采集帧级读写。

### 5.4 App Store 审核风险点(立项必读)
- 后台音频/VoIP 须有真实通话场景支撑,不可挂常驻通知刷在线。
- 涉虚拟商品/充值/提现须符合 IAP 或外链政策;私密付费内容、抽奖/折扣池需评估上架风险。
- 预留审核包灰度开关(对齐安卓 `CommonApp.isReview`),审核期隐藏敏感入口。

## 6. 待产品/后端确认的疑点(立项前澄清)

1. **派对房是否纳入 iOS** —— 排期最大变量(XL)。
2. **NERTC 备用栈** —— 是否退役,iOS 可否只做声网单栈(强烈建议是)。
3. **机器人/虚拟来电**(Robot/Virtual Call、假人通话)—— 业务定位(引流/审核),iOS 是否保留。
4. **代理/公会、转盘** —— 是否为渠道特性,iOS 是否需要。
5. **心跳频率/弱网阈值** —— Web 6s vs 安卓 10s,iOS 取值需后端统一。
6. **死代码确认** —— Web `communication`(旧 news)、`vedioRecorder`(Demo)、`task/conten.vue`、安卓 `keep` 模块(未编译)、Google Billing(已废弃)等,iOS 不应移植。
7. **大R 专页** —— Web 独有,iOS 是否纳入(建议纳入)。

---

## 7. 结论

- 两端在**核心接单链路(直播/通话/IM/钱包/账号/任务)高度一致**,iOS 可直接以安卓为蓝本 + 共用后端快速实现第一期 MVP。
- **最大差异是派对房(仅安卓、XL)**,其次是进阶美颜、亲密度、计费定价、代理体系(均以安卓为唯一/完整来源)。
- iOS 的**主要新工作量不在业务逻辑(后端已就绪),而在平台特性重写**(保活→PushKit/CallKit、Apple 登录、深链、美颜 SDK 集成)与 **App Store 合规改造**。
- 协议字段(第 4 节)是一致性保障的重中之重,建议立项时整理成跨端协议对照表持续维护。
