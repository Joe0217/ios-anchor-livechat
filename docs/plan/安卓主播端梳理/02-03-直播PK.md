# 直播 PK 业务域 — 模块级业务逻辑梳理(Web / 安卓双端)

> **需求** DM-20260616-004 · **阶段二交付物**(对应需求步骤2)· 业务域 T0-3

## 1. 业务目标与定位

主播间实时连麦对战:两个独立直播间的主播通过跨房音视频连麦同屏(左右分屏),在限定时长内比拼观众打赏贡献值,时间到判定胜负,进入惩罚(表演)阶段。发起方式有两种:**随机匹配**(系统按池子撮合相近主播)和**定向邀请**(搜索/推荐列表点名邀请)。观众侧(客态)只观看 PK 进度与结果动画,不参与控制。

两端能力对齐度高(同后端、同云信通道、同 Agora 频道协议),差异主要在前端实现栈与少量交互细节。

## 2. 核心业务流程(分步)

### 2.1 Web 主播侧(h5-anchor)

状态机集中在 `src/stores/modules/livePk.js`(Pinia `useLivePkStore`),状态枚举见 `src/constant/livePk.ts`:`Live → Matching/Inviting/Invited → InPK → Punishing → Live`。

- **随机匹配**:`startRandomMatch()` 调 `startPkMatch`,进入 `Matching`。两阶段:QUICK(15s,A 池,3s 轮询)→ 超时切 RETRY(默认 5min,B 池,10s 轮询,再调 `startPkMatch{isMatchRetry:true}`)。轮询本身不判定结果,撮合成功由后端 WS 推送。重试超时则自动 `cancelMatch('timeout')` 并打"匹配失败"标记。
- **定向邀请**:`inviteAnchor()` 调 `invitePk`,进入 `Inviting`,最多同时邀请 5 人(本地 `invitedList` 维护,每条 60s 本地超时)。被邀请方收到后用 `handleInvite` 上报 接受(1)/拒绝(2)/超时(3)/取消(4)。
- **匹配成功 / 邀请被接受**:`handleMatchSuccess()` / `handleInviteAccepted()` 收到后立即置 `isJoiningPk=true`(保证直播间心跳上报 `callState=3`),调 `joinPk`(`pkType` 1 随机 / 2 邀请)拿回 `pkId`、对方 `agoraChannelId`、`yxAccId` 等,进入 `startPk()`。
- **PK 进行**:`startPk()` 置 `InPK` + 5 秒准备倒计时(`startPreparingCountdown`),同时立即按 `endTime` 启动 `startPkCountdown()`(准备阶段与 PK 倒计时并行启动,准备结束发"PK 开始"公屏)。`pkBattleView.vue` 监听 `isInPkOrPunishing` 创建 PK 专用 RTC 客户端订阅对手频道视频流。倒计时归零调 `endPkWhenTimeUp()`(`endPk` 接口,`isActiveDisconnect:1`)。
- **结算**:后端推送进入惩罚阶段,`endPk(resultData)` 把 `result`(1 胜 / 2 负 / 3 平)映射成 `win/lose/draw`,置 `Punishing` + 120s 惩罚倒计时,发结果公屏 + 贡献榜 Top3 公屏(`getPkTop3RankList`)。惩罚倒计时结束 `endPunishment('countdown')` → `endPunishing` 接口 → `disconnectPk` 回到 `Live`。
- **中断 / 断开**:`interruptPk()`(PK 中主动中断,`disconnectFromStatus:7`)、`disconnectPk()`(惩罚中手动断 `disconnectFromStatus:8`)。

### 2.2 Android 主播侧(android-anchor)

发起 UI 在 `LivePkDialog.kt`(底部弹窗:随机匹配区 + 推荐/搜索主播列表 + 时长设置 + 记录 + 规则 + 接收邀请开关)。业务编排核心在 `call/agora/ui/LiveCallActivity.kt`,事件靠 **LiveEventBus(`Const.EVENT_LIVE_PK_CHANGED` + `LivePkAttachment`)** 串联,状态码见 `library/constants/PkConstants.kt`(0 普通 /3 匹配 /6 被邀请 /7 PK 中 /8 惩罚 /9 断开 /10 即将进入 /-1 对方断线)。

- 匹配:`LivePkDialog.startMatch()` 本地起 15s 快速倒计时(`MatchPkEntity.completeQuickTimeMills`),回调 `onStartMatch` 上报,超时切扩大匹配(`pk_second_match.svga`)。
- 邀请:`invitePk()` 调 `inviteHost`,列表项 `pkStatus` 切 2(等待);最多 5 个(`LivePkInvitationCancelDialog` 管理取消)。被邀请方用 `LivePkInvitationReceivedDialog`(居中弹窗,60s 倒计时,接受=1/拒绝=2)。
- 建连:`LiveRoomMsgFragment.joinPk()` 调 `joinPk` 接口拿 `JoinPkEntity`(含 `pkId/agoraChannelId/pkEndTime`),发 `TYPE_PK_START` 事件 → `LiveCallActivity.startPkConnection()`:播放 `pk_pre_start.svga`,按 `endPkTimeMills` 起倒计时,剩 5s 播 `pk_pre_end.svga`,调用 `mLivePkManager.joinRemoteRtc(...)` 订阅对手视频。
- 结算:`TYPE_PK_END` → `startPkPunish()` 按 `result` 播 `pk_result_win/loss/draw.svga`,起惩罚倒计时,完结 `stopPkConnection()`(`mLivePkManager.stopRemoteRtc`)。

## 3. 关键接口 / SDK

**HTTP 接口(同后端,前缀 `/api/pk/`)**——Web `src/api/livePk/index.ts`;Android `call/http/HttpHelper.kt` 一一对应:

|---|---|---|
| 发起/重试随机匹配 | `startPkMatch` | `startPkMatch` |
| 取消匹配 | `cancelMatch` | `cancelMatch` |
| 加入 PK(取 pkId) | `joinPk` | `joinPk` |
| 发起邀请 | `invitePk` | `inviteHost` |
| 处理邀请(接受/拒/超时/取消) | `handleInvite` | `handleInvite` |
| 结束 PK | `endPk` | `endPk` |
| 结束惩罚/中断 | `endPunishing` | `endPunishing` |
| 贡献榜/Top3 | `getPkRankList`/`getPkTop3RankList` | `getPkRankList` |
| 主播列表/记录 | `getRecommendAnchorList`/`getPkRecordList` | `queryLivePkHostList`/`getPkRecordList` |

| 邀请开关 查/改 | `queryInviteSwitch`/`updateInviteSwitch` | 同名 |
| PK 状态查询(重连) | `getPkStatus` | `getPkStatus` |

**跨房连麦(Agora)**:核心在于"加入对方的 Agora 频道、以观众角色只订阅不发布"。
- Android `LivePkManager.kt`:`RtcEngineEx.joinChannelEx(rtcToken, RtcConnection(对方channelId, 本地uid), options)`,`options` 全部 `publish*=false` + `clientRole=AUDIENCE` + 超低延时;`setupRemoteVideoEx` 渲染到 `iBroadcasterBView`;`muteRemoteAudioStreamEx` 实现静音;监听 `onRemoteVideoStateChanged`,对方 STOPPED/OFFLINE 触发 `onDisconnect`。
- Web `pkBattleView.vue`:`createClient({mode:'live',role:'audience'})` 新建 PK 专用 client,`join(对方 agoraChannelId)` 后监听 `user-published` 只订阅匹配 `opponentUserId` 的流,播到右侧容器;左侧用主播本身美颜画面(共用直播推流)。

**实时消息**:Web 走云信(NIM)聊天室自定义消息;Android 走云信 + 部分 Agora RTM。两端公屏通知统一 `type:'pk_notification'`, `attachType:-9`;静音广播 `attachType:-8`。

## 4. 状态与数据流

**WS 消息驱动是核心**。后端通过云信自定义消息(`attachType` 97/98/99/100)推送,前端据此驱动状态机:

- Web 入口 `live.js` 的 `handlePkMessage(ext)`(行 521-624),按 `attachType` 分发,并用 `isAnchor` 区分主态/客态:
  - `97` 收到邀请 → `handleReceiveInvite`
  - `98` PK 值+贡献榜实时更新 → 主态 `updatePkValueAndContributors`(取 `pkCounter/oppositePkCounter/top3User/oppositeTop3User`),客态 `audiencePkStore.updatePkData`
  - `99` 邀请状态变更(1 接受 /2 拒 /4 取消)
  - `100` 用内嵌 `data.pkStatus` 细分:`7` 客态进 PK / `8` 进惩罚 / `9` 对方结束惩罚或中断 / `10` 匹配成功 / `-1` 对方异常断线
- Android 入口 `LiveRoomMsgFragment.kt`(行 1599+):`PK_INVITE_NOTIFY` 弹接收邀请框;`PK_INVITE_STATUS_NOTIFY` 接受时调 `joinPk`;`PK_STATUS_NOTIFY` 按 `pkStatus`(10 匹配成功 /7 PK 开始 /8 惩罚 /9 断开)封装成 `LivePkAttachment` 发 LiveEventBus,由 `LiveCallActivity` 消费。

**贡献值实时更新**:纯消息驱动(`attachType=98`),不轮询;前端只做展示和进度条比例计算(Web `myPkProgress`,Android `handlePkGiftChange` 把比例 clamp 在 0.12~0.88)。

**倒计时同步**:以服务端下发的 `endTime`/`endPkTimeMills`(绝对时间戳)为准,本地 `setInterval`/`Flowable.interval` 仅做秒级递减显示,避免累计漂移。最后 5 秒触发专属动画(Web `Last5sCountdownAnimation` / Android `pk_pre_end.svga`)。

## 5. 边界与异常

- **匹配失败**:快速匹配超时切扩大池,再超时取消并提示(Web `matchFailedByTimeout` 标记 → `pkMatchFailedPopup.vue`;Android Toast)。
- **对方断线**:Agora 远端流 STOPPED/OFFLINE → Android `LivePkManager.onDisconnect`;后端检测连续 ~20s 无心跳推 `pkStatus=-1` → Web `handleOpponentAbnormalDisconnect` 调 `endPunishing(isActiveDisconnect:3)` 后等后端通知统一收尾。
- **本端网络中断重连**:Web `syncPkStateAfterReconnect()` 调 `getPkStatus`(返回 `'INPK'/'PUNISHING'/null`)与本地状态比对,不一致则强制 `cleanupAllPkStates` 或重建惩罚倒计时;Android `LiveRoomMsgFragment` 行 765 同样用 `getPkStatus` 字符串比对纠偏。
- **PK 中途退出**:`interruptPk`(`disconnectFromStatus:7`)/惩罚中断(`:8`);双方都会收到 `pkStatus=9`,靠 `isActiveInterrupt` 区分主动方与被动方提示文案。
- **关播兜底**:Web `cleanupAllPkStates(reason)` 按当前状态依次取消匹配/断开连线/清邀请/清定时器,并有 catch 内强制重置。
- **重复消息防护**:各 `handleXxx` 入口都有状态校验(已在 PK 中忽略匹配成功、已有 `receivedInvite` 忽略新邀请等)。

## 6. Web vs 安卓差异提示

- **实现栈**:Web = Pinia 单一 store 管全状态 + Vue 组件 + agora-rtc-sdk-ng(observer/computed 驱动 UI);Android = LiveEventBus 事件 + Activity/Dialog 命令式 UI + RtcEngineEx + SVGA 动画。
- **状态表示**:Web 用字符串枚举(`PK_STATUS`)做主态机,再额外引后端数字 `pkStatus` 解析 WS;Android 直接用数字 `PkConstants`。语义一致。
- **匹配阶段时长**:均为 15s 快速 + 可配置扩大阶段(后端 `pk_match_duration`,默认 300s)。
- **主态 vs 客态**:Web 主态 `useLivePkStore` / 客态 `useAudiencePkStore` 完全分离;客态只接收 `98`(更新)/`100`(进 PK/惩罚/结束),无控制能力。Android 客态在 `LookLiveActivity.kt`。
- **动画差异**:Web 用一组 `*Animation.vue`(准备倒计时/最后 5 秒/结果/双方信息);Android 用 assets 下的 `.svga`(`pk_pre_start/pre_end/result_win/loss/draw`)。视觉节点对齐。
- **静音**:两端都调 `mutePkRoom` + 广播 `attachType=-8` 给观众同步。

## 7. iOS 实现注意点

1. **跨房连麦是关键**:复用主播自己的直播频道做左侧本地画面,**新建一个 Agora 连接以观众角色 join 对方 channelId、只订阅不发布**(对标 `joinChannelEx` + `publishX=false` + `AUDIENCE` + 超低延时)。退出 PK 必须 `leaveChannelEx` 释放该连接。
2. **状态机以 WS 为唯一真相源**:照搬 `attachType` 97/98/99/100 与内嵌 `pkStatus` 7/8/9/10/-1 的分发表;接受邀请/匹配成功后先调 `joinPk` 取 `pkId` 再进 PK。
3. **倒计时用绝对时间戳**(`endTime`/`pkEndTime`)本地递减,勿用纯计数;准备 5s 与 PK 倒计时并行;最后 5s 动画。
4. **重连纠偏**:恢复前台/断网重连后调 `getPkStatus`(`INPK`/`PUNISHING`/`null`)与本地比对强制同步,避免卡死在已结束的 PK。
5. **异常断线**:监听远端视频流状态 + 后端 `pkStatus=-1`,调 `endPunishing(isActiveDisconnect:3)` 收尾。
6. **结算原因区分**:`endPk`/`endPunishing` 的 `isActiveDisconnect`(1 正常 /2 主动 /3 断线) 与 `disconnectFromStatus`(7 PK 中 /8 惩罚中) 组合需与后端严格一致;中断时双方靠 `isActiveInterrupt` 区分提示。
7. **心跳一致性**:进入 PK 流程瞬间需让直播心跳上报"PK 中"(对标 Web `isJoiningPk`/`callState=3`),否则后端可能误判断线。
8. **公屏/静音消息协议**:PK 开始、结果、Top3 贡献榜公屏统一 `type:'pk_notification'` `attachType:-9`;静音 `attachType:-8`,需与 Web/安卓字段一致。
