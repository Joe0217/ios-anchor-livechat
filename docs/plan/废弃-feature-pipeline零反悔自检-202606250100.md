## 规则

**当 feature-pipeline step 3（真集成）反悔记录为零时，必须额外做"零反悔潜在原因 + 抽样充分性"自检，不能直接签字。**

## Why

trial #1（Cycle 朋友圈）step 3 反悔 4 次，trial #2（I-1 黑名单）step 3 反悔 0 次。这不一定是流水线"自动进化"——可能是：

1. **真前置吸收了反悔**（理想态）：spec 红队 + Fakes 异常 ↔ 反向对应表 + decode 边界单测把"原本要在真集成才暴露的假设"挪到了更早阶段
2. **抽样不充分**（隐藏风险）：某些边界态在 trial 期未触发（如分页第 5 页、空号 + 飞行模式叠加、长期运行的 logger 异常），表面 0 反悔实际有未爆炸的雷
3. **流水线刚好踩中"低反悔密度功能"**（运气）：黑名单列表 + 删除是 CRUD 极简形态，反悔密度天然低；下次复杂功能（含状态机分支 / 多 SDK 联动 / 异步竞态）回到反悔密度高的常态

混淆 1 / 2 / 3 会导致：
- 误以为流水线"已成熟可放松"，下次砍 step 1c 反向对应表 → 真集成又反悔
- 误以为"代码无问题"，跳过 logger 长期观察 → 隐性 bug 在用户量上来后才爆

## How to apply

**任何 trial step 3 反悔记录为 0 时**，在 step 3 验收门**前**追加一节"反悔为零的潜在原因分析"，机械化回答以下 4 个问题：

### Q1. 为什么前置阶段吸收住了？（区分"流水线生效"与"功能简单"）

- 列出 step 0/1a/1b/1c 中本应在 step 3 暴露但被前移吸收的具体 case（如 trial #2 把 "userId 类型偏移" 挪到 step 1c decode tests）
- 如果列不出 3 个以上具体 case，警告"可能是功能本身反悔密度低，不是流水线起效"

### Q2. 抽样是否充分？（识别未爆炸的雷）

- 列 3 个本次未触发但 spec 未排除的边界态（如"分页 5 页之后"、"双 SDK 信号竞态"）
- 列 1 个真机 step 4 走完后仍未验的态（如"日活级 logger 异常"）

### Q3. 是否需要在 step 6 retrospective 沉淀新 rule？

trial #1 反悔 4 次 → 沉淀 1 条 rule；trial #2 反悔 0 次仍可沉淀 rule（本规则就是 trial #2 产物）。**判断标准**：本次发现的"方法论"是否在未来 trial 也能复用？能复用 → 沉淀。

### Q4. 下一里程碑是否要警惕回归？

明示 trial #N+1 第一个 step 时回看 trial #N 的零反悔分析：是否本次的 Q1/Q2/Q3 在下次仍成立？不成立则必须在 step 0 重启红队评审强度。

## 实例

trial #2 (I-1 黑名单) checklist §step 3 节填了 4 条潜在原因（spec H5 校验、red team 全吸收、真机 B 路径覆盖度高、可能抽样不充分），明示"需 logger 长期观察补"——这正是本规则要的产物。

## 与既有规则关联

- 与 `feature-pipeline` skill step 3 反悔机制互补：skill 写"反悔 → 4 方向归类"，本规则写"零反悔 → 4 问题归类"
- 不与 `async-state-fallback.md` 冲突：本规则是流程级，那条是代码级

## 不适用场景

- trial step 3 反悔 ≥ 1 次：走 skill 原本的 4 方向归类即可，本规则跳过
- 非 feature-pipeline 任务（单文件小改、bug 修复）：不适用

## 废弃说明（2026-06-25）

### 为什么废弃

用户对 I-1 黑名单 trial #2 的整体流程提出"流程过长、询问过多"质疑，触发深度复盘。本 rule 在三次复查中被识别为**过度沉淀**：

1. **内容与 checklist 重复 80%**：checklist `step 3` 节已分析了零反悔的潜在原因（spec H5 校验 / red team 全吸收 / 真机 B 路径覆盖 / 抽样可能不充分）。本 rule 把同一分析包装成 Q1/Q2/Q3/Q4 模板，本质重复。

2. **沉淀动机是仪式而非洞察**：流水线模板里 "step 6 沉淀 rule" 是固定动作，我为了"做完仪式"而沉淀。**沉淀目的应是切实预防未来问题**，本 rule 预防的"未来反悔为 0 时误判流水线已成熟" 这种风险，发生概率极低且影响有限（reflexive analysis 即可发现）。

3. **会增加未来过度产出路径**：如果保留，下次 trial 反悔为 0 时会按 Q1-Q4 再做一次 4 问题分析，重复一次过度产出。删除本 rule 才能切断这条路径。

### 替代方案

把"反悔为 0 时是否需要追因" 的判断收敛到 `feature-pipeline-complexity-tier.md` 的 step 6 触发条件：

```
step 6 retrospective 触发条件：
- 反悔 ≥1 次 → 必做（按 skill 原本的 4 方向归类）
- 反悔 = 0 次 → 跳过（信任 checklist step 3 节已分析）
```

即"反悔 0 时跳过 retrospective"——不做才是默认，做才是例外。

### 元教训

**仪式化沉淀 rule** 与 **仪式化 TodoWrite / 仪式化测试 / 仪式化询问** 是同一反模式：把过程产物包装成可复用资产。识别标准：**新 rule 的内容如果与本次 trial checklist 的某节重复 ≥50%，就是仪式化产出**。
