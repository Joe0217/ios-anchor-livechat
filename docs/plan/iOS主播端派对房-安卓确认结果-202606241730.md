## 一、WebSocket 心跳协议

### 后端真值（决定一切）
WS 网关 `weidou-socket` 入站只认 3 个 `messageType`（`MyWebSocketHandler.java:73-93`，枚举 `MessageModelType.java:7-9`）：

| messageType | 含义 | 调用链 | 是否刷新派对心跳键 `user:online:party:room` |
|---|---|---|---|
| **1** REPORT_STATUS | 上报状态 | `reportStatusHandler(...,userType=2,...)`（写**主播**在线表 `ANCHOR_WEBSOCKET_ONLINE`）+ **`partyRoomHeartbeat()`** | ✅ 是 |
| 2 USER_UPDATE_STATUS | 改状态 | `reportStatusHandler(...,userType=1,...)`（写用户在线表） | ❌ 否 |
| **3** USER_KEEP_HEARTBEAT | 保活 | `userKeepHeartbeatHandler()`（写用户在线表）+ **`partyRoomHeartbeat()`** | ✅ 是 |

- 只有 `partyRoomHeartbeat()`（`WebSocketOnlineUserConfig.java:431-445`）写 `lastActiveTime`；它被 **type=1 和 type=3 都调用**（`MyWebSocketHandler.java:79`、`:92`）。
- **关键守卫**（`WebSocketOnlineUserConfig.java:435-436`）：仅当 `onlineStatus==PARTY_ROOM` **或** `roomId>0` 才写键；否则走 else 清理分支（`:498-507`，且仅在 15 分钟后才删旧记录）。
- 30s 踢人读同一键、同一字段（`PartyRoomSeatServiceImpl.java:603,626`，阈值 `>1000*30`，**全员统一、主播无豁免**）。
- `partyRoomHeartbeat` 只读 `onlineStatus`(toInt)、`roomId`(**toLong=数字**)、`seatIndex`(toInt)三个字段（`:433-437`）；**不读 `channelId`、不读 `userStatus`**（userStatus 仅 type=3 的 `userKeepHeartbeatHandler` 在 `:239` 读，用于 Lucky Slots/停留时长）。

### 安卓主播端实际行为
- **只有一条统一心跳**：`messageType=1` 固定（`OkWebEntity.java:36`），把派对 `roomId/seatIndex` 合进同一条 `expandParams`（来自全局 `LibApp.partyRoomId/partyRoomSeatIndex`）。**没有独立的 type=3 派对心跳**。
- 间隔 **15s**（`VptWebSocketManager.java:43`，`scheduleWithFixedDelay`）。
- `expandParams` 实际只有 `{onlineStatus:Int, roomId:String, seatIndex:Integer}`（`OkWebEntity.java:21-23`）；**无 `channelId`、无 `userStatus`**（等价物是 `onlineStatus`）。
- `roomId`=**String**；`seatIndex`=麦位号(1-13)，**未上麦时为 `null`→Gson 直接省略该字段（不是 -1）**（`OkWebEntity.java:40`、`PartyRoomDataManager.kt:1308-1316`）。
- 不在派对房：心跳照发（用户级、登录后常驻），`roomId/seatIndex` 两个 key **直接消失**（null 被省略）（`PartyRoomDataManager.kt:1372-1373`）。
- `requestId`=**每条新 UUID**（`OkWebEntity.java:27,35`），**不是** DeviceId。

### 逐项回填
- **1.1 messageType** ⚠️：派对应走 **`messageType=1`**（非 3）。iOS「1走直播/3走派对」的双心跳模型与安卓不符。安卓主播用 type=1 落「主播在线表」并同时刷新派对键；若 iOS 用 type=3，会落「用户在线表」而不刷新主播在线态。**完整枚举**：1/2/3 见上表，其它值静默忽略。**主播专属 type**：无，主播身份由「发哪个 type」决定（type=1→userType=2 主播语义，硬编码于 `MyWebSocketHandler.java:77`），不读 expandParams。
- **1.2 expandParams** ⚠️：真值字段 = `onlineStatus / roomId / seatIndex`。`channelId`、`userStatus` **后端不读、安卓不发**，iOS 可删（传了也被忽略，无害但无用）。`seatIndex` 字段名正确，值=麦位号；未上麦安卓用 **null（省略）**，iOS 现用 -1 可工作（后端 toInt 容错）但与安卓不一致，建议对齐为「不在麦位则不带该字段」。`roomId` 类型：后端 `Convert.toLong` **数字/数字字符串都接受**；安卓发 String；iOS 发哪种都行，但**必须可转成 >0 的数字**。`userStatus`：派对心跳(type=1)路径**完全不读**，主播无错误计费风险。
- **1.3 间隔** ⚠️：安卓 **15s**；后端注释期望 ~20s；硬上限：`USER_PARTY_ROOM_STATUS` TTL **25s**（`:452`）、麦位踢人 **30s**（`:626`）。→ iOS 间隔须 **<25s**（建议 15s 对齐安卓）。**30s 阈值对主播无差异**（`checkUserRoomHeartbeat` 无角色分支）。
- **1.4 requestId** ℹ️：安卓=随机 UUID/条；后端**未发现依赖 requestId 去重/会话追踪**（否则随机 UUID 会失效）。iOS 用 DeviceId 安全，用随机 UUID 也安全。
- **1.5 是否常驻发** ⚠️：安卓是**用户级常驻**（连上 WS 即发，与是否在派对房无关，进房只是往 expandParams 填 roomId）。**强约束**：在派对房时**每条心跳必须带 `roomId>0`（或 `onlineStatus=PARTY_ROOM`）**，否则 `partyRoomHeartbeat` 走清理分支不刷新键 → 30s 被踢（`:435-436,498-507`）。iOS「仅 partyContext 非空才启 timer」可行，但更稳妥是对齐安卓：复用既有 type=1 心跳，进房时注入 roomId/seatIndex 即可，无需第二条心跳。

## 二、派对房 HTTP 接口

### 2.1 enter ✅(部分)/ℹ️
- `isAnchor`：DTO `EnterRoomRequest.java:28` = **Boolean，默认 false**；安卓恒发 `true`（`HttpHelper.kt:249`）。
- ℹ️ **后端只用它做一件事**：`true` 时在响应里塞主播私call设置（`partyPrivateCallOpen/partyCallGiftId/...`，`PartyRoomServiceImpl.java:1260-1281`）。**不绕过密码**（密码校验只看 `lockFlag` + 是否房管，`:1105-1110`）、**不给座位优先**、**不影响在线统计**。
- 响应角色字段 ✅：`EnterRoomResponse.roomRoleType` = Integer（1房主/2房管/3普通，`:92`）+ `isPlatformAdmin`(Boolean) + `roomAdminCount`(Long)。

### 2.2 onSeat / downSeat ⚠️
- 入参 DTO `RoomOnSeatRequest`：`roomId`**Long** / `seatIndex`**Integer** / `yxRoomId`**String** / `roomTempId`**Long**(默认1L) / `isSelf`Boolean / `isAdmin`(服务端置) / `byInvite`(`@JsonIgnore`，客户端不可传)。
- ⚠️ **`roomTempId` 全系统都是 `Long`**（`RoomOnSeatRequest.java:39`、`EnterRoomRequest`、`RespondInviteRequest`、`InviteOnSeatRequest` 同），安卓发 Long（`HttpHelper.kt:381`）。**iOS 的 String 需改为数字**。
- 排队 vs 直接占座 ⚠️：后端 `PartyRoomSeatFacadeImpl.java:145,150-154`：`isAdmin(房主/房管/平台管理员) || 房间申请开关关` → `doOnSeat` 立即占座；否则 → `queueOnSeat` 入队（需 `agreeSeat` 审批）。**这是按「房内角色」判定，不是按「主播账号类型」**。即：一个仅是观众身份的主播，进了开了「申请上麦」开关的房，**仍要排队**。客户端**调同一个 onSeat 接口**，由服务端决定是否入队 → iOS 必须能处理「已入队」返回，而非假定立即上麦成功。

### 2.3 updateMedia ✅/ℹ️
- DTO `UpdateCameraMicRequest`：`type`**Integer**（**1麦/2摄像头/3麦+摄像头**，`:26`，iOS 漏了 3）、`enable`**Integer 0/1**（`:32`，确认是 Int 不是 Bool）、`roomId`Long、`seatIndex`Integer、`yxRoomId`String。
- ℹ️ 接受视频位邀请时安卓会调 `updateMedia(type=3,enable=1)` 自动开摄像头 → iOS 需支持 type=3。

### 2.4 sendGift ✅/ℹ️
- DTO `PartyRoomSendGiftRequest`：`scene`String(默认`"PARTY_ROOM"`)、`yxAccidList`**List<String>=云信accid**(非userId)、`giftId`**Long**、`num`**Integer**、`roomId`Long。安卓 `scene` 同为 `"PARTY_ROOM"`、`yxAccidList` 取 `seat.yxAccid`（`PartyRoomGiftDialog.kt:229`）。
- ℹ️ `num`：后端 DTO 是 **Integer**；安卓发 String（Jackson 容错），iOS **建议发数字**。
- **主播给主播** ⚠️：`scene` 无需特殊值。后端确有主播分支但只影响**钱包/收益侧**：发送方主播扣**主播钻**(`updateAnchorDiamond`)而非用户钻、且不记用户消费/用户任务（`PartyRoomFacadeImpl.java:659-669,330-335`）；接收方主播若**在麦+房间TOP3**触发「上麦任务 gems 加倍」（`PartyRoomGiftServiceImpl.java:479-516`，命中当天首次发 P2P **1029**）。**没有「主播互送不计收益」的特殊路径**，只会更多不会更少。
- 上限：后端**只校验 `num>0`**，无 num 上限、无收礼人数上限（唯一约束：每个 accid 必须能查到用户）；真正天花板是发送方余额。安卓客户端侧 `num` 受礼物档位配置限制、收礼人至少 1。

## 三、NIM attachType payload（后端为发送方=真值）

### 3.0 信封（所有聊天室消息通用，先读）
`NetEaseChatRoomServiceImpl.java:301-337`：NIM 自定义消息 `msgType=100`，`ext = {"attachType":<Number>, "data":<data>}`。`data` 三种形态：①**对象**（caller 传 Map）；②**JSON 字符串**（caller 传 `JSON.toJSONString`，需二次 parse）；③**Base64(GZIP) 字符串**（`JsonCompressionUtils.compressJson`）。gzip 异常时退化为**纯 Base64 无 gzip**（`:34`）→ 解压前判 magic `0x1f8b`，否则按 UTF-8 明文。P2P 消息（1029/1040-1048）走 `sendAttachMsg`，**无外层 data 信封**，map 顶层直接带 `attachType`。

### 逐项
- **3.1 1001（后端名 `SEAT_OR_UNMUTE_SEAT`）** ⚠️：顶层数组 key=**`seats`**（不是 seatList/mikeList/list/data）；**全量麦位**；变更原因字段=**`seatOperate`**（非 operatorType）；**gzip=是**；广播全房。安卓同样解 `seats`+`seatOperate` 全量替换（`PartyRoomVM.kt:400-460`、`PartyRoomSeatUpdateInfo.kt`）。`seatOperate` 值(`SeatOperationTypeEnum`)：**1上麦/2下麦/3抱下麦/4抱上麦/5换麦/6禁麦/7解禁/8锁麦/9解锁/10交换/11取消管理抱下**。→ iOS「1=上麦 2=下麦 6=禁麦」中 2/6 对，**1 实为 APPLY_ON_MIKE**；wrapper key 猜测全错，应固定 `seats`。
- **3.2 1012（后端名 `ROOM_MUSIC_EXIT_SEAT`）** ⚠️：payload=`{seatIndex, roomId}`，**`roomId` 是 Number**；`seatIndex`=刚空出的麦位；**非 gzip**（data 是 JSON 字符串，需二次 parse）；广播全房。安卓收到 1012 = **直接 `loadMikeList()` 全量重拉**，不读 payload（`PartyRoomVM.kt:523-525`）。**无「被踢专用字段」**，无法区分「心跳超时/换房/兜底」——三者都复用 1012 同 2 字段。区分「自己被踢」要看 **1003**（见 3.4）。
- **3.3 2049（`..._COMPRESSED`）** ⚠️：**gzip=是**；全房。真实字段（解压后）：`giftId`(Number)、`giftNum`(Number，**不是 num**)、`giftIcon`、`giftPrice`、`giftType`、`smallImg`、`sendUser`(**对象**：`userId/nickname/icon/yxAccid/userType...`)、`receiveUserList`(**对象数组**，按 `userId`)、`roomId`(Number)、`ownerId`、`gems`、`cost`、`isVip`、`roomRoleType`、`isPlatformAdmin`、`userMedals`。**无 `giftName`**；发送/接收方都是**用户对象**不是裸 id/accid 数组。→ iOS 兜底字段名(`senderUserId/fromUserId/receiverUserIds/yxAccidList`)基本全错，应改用 `sendUser.userId`、`receiveUserList[].userId`、`giftNum`。
- **3.4 1007** ❗：**后端仍在发**，且与 2049 **每次双发**（明文 1007 + gzip 2049，同内容，`PartyRoomGiftServiceImpl.java:833-845`），目的=老客户端兼容。安卓**故意只解 2049、忽略 1007**（避免翻倍，`PartyRoomVM.kt:101-102`）。→ iOS **只解 2049 即可，不会漏礼**；**绝不可 1007+2049 都解**（会翻倍）。去重键只能用 `giftId+sendUser.userId`(+NIM 消息时间)，**payload 无 timestamp 字段**。
- **3.5 1003（后端名 `KICK_ROOM_NOTIFY`，仅「踢出房间」时发，非心跳超时）** ⚠️：payload=`{seatIndex, roomId, userId}`，类型均 **Number**；**无 `kickReason`、无 `operatorUserId`**（封禁类型/操作者只落库不进 payload，`PartyRoomNotificationServiceImpl.java:222-237`）。安卓双字段守卫 `userId==自己 && roomId==当前房` 才退房（`PartyRoomVM.kt:475`），与 iOS 一致 ✅。**心跳超时不是 1003，是 1012**。
- **3.6 1008（`UPDATE_SEAT_MEDIA`）** ✅：payload=`{roomId, seatIndex, seatType, userId, cameraEnabled(0/1), microphoneEnabled(0/1)}`，**非 gzip（嵌套对象）**，广播全房（fromAccid=变更用户）。安卓做**定向更新**对应麦位（非全量重拉，`PartyRoomVM.kt:492-500`）。iOS MVP 收到即全量 reload 可行，后续可优化为定向。
- **3.7 1015（`PROHIBIT_SEAT`）** ✅：payload=`{roomId, seatIndex, seatMicrophoneEnabled(**0禁/1解**), userId, operatorType(**6禁/7解**)}`，**禁麦/解禁同一 attachType**，靠 `seatMicrophoneEnabled`/`operatorType` 区分；非 gzip；全房。安卓据 `seatMicrophoneEnabled` 0/1 切换（`PartyRoomVM.kt:567-598`）。
- **3.8 1040-1048（视频位邀请，P2P）** ⚠️：
  - **1040→被邀请者**：`{attachType:1040, inviteId(String), roomId(Number), yxRoomId(String), seatIndex(Number), ownerUserId(发起人id), ownerNick(发起人昵称), ttl(秒,默认30)}`。**字段名是 `ownerUserId/ownerNick`，不是 `fromUserId/fromNickname`**；安卓额外读 `roomTempId(Number)`。
  - **接受方式 ⚠️**：**不是直接 onSeat**，而是专用接口 **`POST sapi/weidou/v1/client/party/seat/respondInvite`**（DTO `RespondInviteRequest`：`action`Integer **1接受/2拒绝/3超时** + roomId/yxRoomId/seatIndex/inviteId/roomTempId(Long)）。后端接受时内部置 `byInvite=true` 直接 `doOnSeat`（绕过排队与等级校验，`PartyRoomSeatFacadeImpl.java:1574-1583`）。安卓接受后还会 `updateMedia(type=3,enable=1)` 开摄像头。**接口名是 `respondInvite`（不是 respondInviteSeat），dev 已实装**。
  - **1041-1048→邀请人**（除 **1047=公屏广播全房**）：1041接受/1042拒绝/1043超时/1044离开/1045已占用/1046已在麦/1048上位失败；基础字段 `{inviteId, roomId, seatIndex, targetUserId, targetNick}`（1041 多 `needSupervisionConfirm`，1047 为 `{text, roomId, seatIndex, userId}`）。
  - ❗ 安卓侧坑：1040 被邀请者**弹窗未接线**（`EVENT_VIDEO_SEAT_INVITE_RECEIVED` 无观察者、`VideoSeatInviteDialog` 从未 show）→ 安卓被邀请者实际看不到弹窗。**iOS 应自行实现完整弹窗逻辑**，勿照搬安卓的「沉默」状态。
- **3.9 1029** ❗：后端 **`1029=GIFT_DOUBLED_NOTIFY`「上麦收礼 gems 加倍命中」**（P2P，payload `{attachType:1029, gems:Number}`，仅主播在麦命中加倍且当天首次时发，`PartyRoomGiftServiceImpl.java:547-570`）；**私call开关变更是 `1028 PARTY_PRIVATE_CALL_NOTIFY`**。安卓 `NIMMsgAttachType` 把 1029 **双定义**（聊天室通道当私call、P2P 通道当加倍，`:376/:388`）属安卓侧历史不一致。→ **iOS 以后端为准：1028=私call，1029=加倍**。

## 四、主播身份特有逻辑
- **4.1 创建房** ℹ️：`party/room/create` 仅 6 参（`roomName/roomAvatar/greetingMessage/roomLanguage/roomTempId/bgImgId`，`HttpHelper.kt:167-183`），**无 isAnchor、无主播专属字段/默认值**。
- **4.2 OWNER vs AUDIENCE** ⚠️：安卓**不**用 `ownerId==me`，而是信服务端 **`roomRoleType`(1/2/3)+`isPlatformAdmin`**，并在收到房管变更推送(安卓 `TYPE_ADMINISTRATOR_CHANGES`/后端 `1019 SET_ROOM_MANAGER`)时本地翻转（`PartyRoomDataManager.kt:740-754`）。→ **iOS 的 `ownerId==myUserId` 不够**：会漏「房管(2)」与「平台管理员(isPlatformAdmin)」。改用服务端角色字段 + 监听变更推送。
- **4.3 直播↔派对互斥** ⚠️：安卓**有**「直播中/派对中 → 不允许再进派对房」守卫（邀请路径，`isLiveing||isPartying` 弹 toast，`NIMMessageActivity.java:1232-1239`；另有进房重入守卫 `PartyRoomActivity.kt:337-352`）；**反向（派对中→开播）未发现守卫**。→ iOS D 期建议补 LiveStore/PartyStore 互斥守卫（至少对齐安卓的「进派对前判直播/派对态」）。
- **4.4 进派对房后主播主状态** ✅：安卓进房**不改** `onlineStatus`（保持 FOREGROUND；`ENTER_PARTY_ROOM=10007` 是死代码从不下发）。→ iOS 现状「保持默认不变」**与安卓一致，正确**。
- **4.5 isAnchor 其它接口** ℹ️：派对模块内 `isAnchor` **仅** `party/room/enter` 发（两个变体），其余接口都不发（`HttpHelper.kt:249,423`）。

## 五、低优先
- **5.1 接待位** ℹ️：存在（`setHostSeat/closeHostSeat`，`ApiService.kt:435-440`；座位 `isHostSeat:Int 0/1`）。**主播不自动是接待位**，是**仅房主/平台管理员**可手动设置；观众取接待位被拦截 toast。
- **5.2 PartyCall 抢占** ℹ️：派对房内收到 1v1 来电（`callerType==5`）**抢占**派对——下麦+跳 1v1（`PartyRoomDataManager.kt:651-688,690-738`）；其它类型来电在派对内自动拒接。
- **5.3 房币/收益** ℹ️：客户端**无**收益计算逻辑，钻石/gems 全后端算，客户端仅展示 `gems`/余额。
- **5.4 房间通告 1049** ℹ️：`ROOM_ANNOUNCEMENT_MSG=1049` 公屏广播，**仅房主/平台管理员可编辑**（非主播专属、房管也不能编辑，`EditRoomAnnouncementDialog.kt:49`）。
