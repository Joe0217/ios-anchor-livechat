### P1-1 LiveRoomView 顶层观测 NIMChatroomManager 触发整树重算

- 文件：[Sources/Live/LiveRoomView.swift](../../Sources/Live/LiveRoomView.swift):18,269
- 维度：SwiftUI 性能
- 风险：`LiveRoomView` 用 `@StateObject` 持 `NIMChatroomManager`，body 中 `Text("\(nim.onlineCount)")` 注册了对 nim 整个 ObservableObject 的订阅。`NIMChatroomManager` 上 `@Published` 还有 `connected`（chatroom connectionStateChanged 时变）和 `onlineCount`（每条 `.enter`/`.exit` notification 都 +/- 1，活跃直播间 >1Hz）。每次 onlineCount/connected 变化都触发 `LiveRoomView` body 重算 —— 包括 `ZStack` 内 `CameraPreview` / `RemoteVideoView` / `PKOverlayHost` / publicScreen / bottomBar / topBar 全部子结构。已经把 messages 抽到独立 `ChatMessagesStore`（review P1-3）但只解决了一半 —— 同源问题：onlineCount / connected 仍在大 store 上。
- 修复：把 `onlineCount` / `connected` 拆到独立小 store（如 `ChatPresenceStore`），`LiveRoomView` 顶部 topBar 行 269 注入 `PresenceBadge(store:)` 子 view 内部观测，header 业务态对 `LiveRoomView` 顶层透明；或把 `onlineCount` 字段封到独立 `PassthroughSubject` + `.onReceive` 局部更新 `@State`。参照 [.claude/rules/swiftui-keepalive-publisher-isolation.md](../../.claude/rules/swiftui-keepalive-publisher-isolation.md) 方案 A（派生 bridge ObservableObject + removeDuplicates）。

### P1-2 公屏文本拼接用全角中文冒号「：」，ar/tr 语言下排版错误

- 文件：[Sources/Live/NIMChatroomManager.swift](../../Sources/Live/NIMChatroomManager.swift):167
- 维度：iOS 平台规范
- 风险：工程已声明 `CFBundleLocalizations=[en,ar,tr]`（Info.plist:16-20），但公屏每条文本消息拼接为 `"\(name)：\(body)"` 使用了全角中文冒号 U+FF1A。该字符在阿拉伯语 RTL 上下文中不会自动镜像、在土耳其语/英文环境中显示也异于本地排版（应是 ASCII `:` + 空格 或走 L10n 模板）。违反 CLAUDE.md "字符串走 Localizable.strings，禁止硬编码中文/英文" 国际化铁律；阿语用户实际可见公屏所有发言全部带中文冒号，影响产品体感与提审审查（Apple 审核会检查 a11y/i18n 错位）。
- 修复：在 [L10n.swift](../../Sources/L10n.swift) 加 `imChatMessageFormat` 键（en: `"%1$@: %2$@"` / ar: `"%1$@: %2$@"` / tr: `"%1$@: %2$@"`），改为 `String(format: L10n.imChatMessageFormat, name, body)`。若不想 i18n 走全套，至少把 `：` 改成 ASCII `: `（半角冒号+空格），与其他语言一致。

### P1-3 NIMOnlineKeeper.start 早返回绕过 pendingTask 串行链

- 文件：[Sources/Live/NIMOnlineKeeper.swift](../../Sources/Live/NIMOnlineKeeper.swift):26-47
- 维度：Swift 并发
- 风险：`start()` 顶部直接读 `NIMSDK.shared().loginManager.isLogined()` 决定是否早返回 `isLogined=true`。当前一个 `stop()` Task 已派发但 SDK logout 回调尚未完成时，`isLogined()` 仍返回 true，`start()` 提前返回不入队；随后 stop Task 跑完会把本地 `self.isLogined` 写回 false，而调用方以为登录已 OK。账号快速切换 / token 失效自动重登场景下 `isLogined` 状态与 NIM 实际登录态分裂，且后续 LiveTab/聊天室进房 `guard isLogined()` 会通过但实际未登录，触发主播在线态丢失。
- 修复：把 `isLogined()` 早返回判断也搬到 pendingTask 链内：
  ```swift
  pendingTask = Task { @MainActor [weak self] in
      _ = await prior?.value
      if NIMSDK.shared().loginManager.isLogined() {
          self?.isLogined = true; return
      }
      // ... 原 login 流程
  }
  ```
  等同于 `NIMService.login` 内部已有的 `isLogined` 守卫，但必须发生在 prior stop await 之后才有意义。

### P2-1 NIMService.dispatch 迭代 routers 时无快照保护

- 文件：[Sources/Live/NIM/NIMService.swift](../../Sources/Live/NIM/NIMService.swift):217-236
- 维度：Swift 并发
- 风险：`for wrap in routers` 直接迭代 var 数组。整流程同一 MainActor 同步执行，若任一 router 的 `route` 实现内部走 `NIMService.shared.registerRouter / unregisterRouter / unregisterAllRouters`（同步、非 Task 延迟），会在迭代中 mutate 同一数组 → Swift Array iterator 失效 → trap crash。当前 `SystemMessageRouter` 用 `Task { @MainActor in }` 包了所有副作用，`PartyMessageRouter` / `PKNIMRouter` 也未在 route 内 register，所以暂未触发；H 礼物会话或后续 router 实现不知此约束时容易引爆。
- 修复：迭代前快照：`let snapshot = routers; for wrap in snapshot { ... }`，热路径成本 = 一次 array CoW。同时在 `protocol MessageRouter` 注释里加约束：`route` 实现禁止同步调 register/unregister。

### P2-2 NIMService.dispatchSystemNotification 用 `try?` 静默吞 JSON 解码错

- 文件：[Sources/Live/NIM/NIMService.swift](../../Sources/Live/NIM/NIMService.swift):241-252
- 维度：内存与资源
- 风险：[.claude/rules/error-handling.md](../../.claude/rules/error-handling.md) 「禁止空 catch / `try?` 吞错前确认该错误确实可忽略」。此处 `try?` 后只在 guard 失败时 `logger.notice`，没有上报埋点。生产期遇到 sysMsg payload 格式异常（后端字段类型偷换 / 截断）只能从设备日志查到，没法在埋点中聚合统计。[NIMPayloadDecoder.swift](../../Sources/Live/NIM/NIMPayloadDecoder.swift):37 `unwrapDataField` 同样 `(try? JSONSerialization.jsonObject(with:))` 静默——影响面更大（所有派对房 1001/2049/1100-1112 gzip payload 解析失败都被吞）。
- 修复：把 `try?` 改 `do/catch`，在 catch 内 `logger.error` + 上报埋点（至少计数）。或在 `NIMService` 内补 `decodeFailureCount` `@Published`，UI 调试态可见。

### P2-3 NIMChatroomManager.enter 失败路径不回滚 add + hasJoined 提前置 true

- 文件：[Sources/Live/NIMChatroomManager.swift](../../Sources/Live/NIMChatroomManager.swift):54-88
- 维度：内存与资源
- 风险：`hasJoined` 在 line 59 进 `enterChatroom` 之前就被置 true；IM 未登录（line 66-70）直接 push 错误公屏 return，未来 `enter` 再调时 `guard !hasJoined` 命中、永远跳过。`NIMService.enterChatroom` catch 分支（line 80-86）只 push 错误公屏，未 `hasJoined = false`、未 remove delegate、未 clear roomId。结果：(a) 直播 view 二次进入同房间无法重连（hasJoined=true 永久卡死直到 deinit）；(b) chatManager delegate 仍接收同 roomId 消息，processIncoming 内 sessionId guard 通过会触发空 LiveStore 状态。
- 修复：在 line 70 push 后置 `hasJoined = false; NIMSDK.shared().chatManager.remove(self); NIMSDK.shared().chatroomManager.remove(self); self.roomId = ""`；line 84-86 的 catch 路径同样补回滚。

### P2-4 ChatMessagesStore.append 每条消息整数组 publish，未做 batch

- 文件：[Sources/Live/NIMChatroomManager.swift](../../Sources/Live/NIMChatroomManager.swift):16-23
- 维度：SwiftUI 性能
- 风险：`ChatMessagesStore` 内 `messages` 是 `[ChatMessage]` `@Published` 数组，每条 append 都触发整数组 publish 一次。活跃直播间一秒可来 10+ 条消息，`PublicScreenList` body 每秒重算 10+ 次（虽然 ForEach 用 UUID Identifiable，diff cost 可接受；但 `.suffix(6)` 仍每次重新 evaluate）。短时间洪水（如系统下发批量公屏消息）会引发可感 jitter。`processIncoming` 已有循环（line 110-184）能累积 items 后批量写入 — 该循环本来已 batch，但当前调用 `push()` 是每条单写。
- 修复：`processIncoming` 在 line 187 改成 batch 一次写入：`if !items.isEmpty { messagesStore.messages.append(contentsOf: items); messagesStore.trimIfNeeded() }`；或在 `ChatMessagesStore` 上加 `func appendBatch(_ msgs: [ChatMessage], limit: Int = 80)` 内部一次性 mutate 触发一次 publish。

### P2-5 NIMOnlineKeeper.@Published isLogined 在非 ObservableObject 类上无效

- 文件：[Sources/Live/NIMOnlineKeeper.swift](../../Sources/Live/NIMOnlineKeeper.swift):14-17
- 维度：SwiftUI 性能
- 风险：`NIMOnlineKeeper` 标 `final class` 未继承 `ObservableObject`，但属性标 `@Published private(set) var isLogined: Bool = false`。`@Published` 在非 `ObservableObject` 类上虽然编译通过（创建独立 Publisher），但无法触发 SwiftUI 重算，view 想观测此字段（如 root 切登录态）会被默默吞掉。当前 grep 显示无 view 订阅，是无声 bug 而非显性 bug，但属于易出错的不一致 API 形态——后续路线图 I/J 期任何想用 `isLogined` 驱动 UI 的代码都会踩坑。
- 修复：二选一：(a) `NIMOnlineKeeper` 改 `final class NIMOnlineKeeper: ObservableObject`，与 `NIMService` 同形态；(b) 去掉 `@Published` 标记，明确 `isLogined` 只是普通可读属性，view 订阅长连接态走 `NIMService.shared.$connectionState`。

### P2-6 PartyRoomChatManager.enter 失败路径不回滚 delegate 注册

### P2-7 PartyMessageRouter 字典 keys 日志 .public / .private 不一致，远端可控 key 名可能在 Release 日志泄露 PII

- 文件：[Sources/Party/NIM/PartyMessageRouter.swift](../../Sources/Party/NIM/PartyMessageRouter.swift):49,81,123,142
- 维度：安全与隐私
- 风险：NIM 自定义消息的 `remoteExt` / `payload` 字典 key 名由任意聊天室成员构造（云信对 custom 消息 ext 字段不做 schema 校验）。第 49 行已显式按威胁模型把 `Array(ext.keys)` 标 `privacy: .private`，理由注释明确『若攻击者在 key 名里夹带 PII（如 "userId_123456"）会泄漏』。但 81/123/142 三处用同种来源（remoteExt / payload）的 keys 列表却标 `privacy: .public`——Release 包真机日志直接落盘，威胁模型与 49 行同源。实际利用面：恶意成员发送 `{"attachType":1012, "userId_<受害者id>":"", ...}` 这类构造消息即可在主播端日志服务（如有 sysdiagnose / Crashlytics breadcrumb 抓取系统日志）外泄受害者 id。
- 修复：把 81/123/142 三处的 `Array(ext.keys)` / `Array(payload.keys)` 统一改为 `privacy: .private`，与 49 行保持一致；调试期需看具体 key 名时通过 dev profile / Console.app 直读（.private 在 dev 工程未被遮蔽）。同时建议把『远端可控字典只能 .private 输出』写入 `.claude/rules/log-privacy.md` 一条，避免后续 F/H/I/J 期新加 router 时再次踩坑。

### P2-8 PartyRoomHeaderView 仅读 onlineCount 却整 observe chat 导致 messages 串扰

- 文件：[Sources/Party/UI/PartyRoomHeaderView.swift](../../Sources/Party/UI/PartyRoomHeaderView.swift):17,26
- 维度：SwiftUI 性能
- 风险：`PartyRoomHeaderView` 用 `@ObservedObject var chat: PartyRoomChatManager` 但 body 仅读 `chat.onlineCount`。`chat` 上 `@Published var messages` 在活跃派对房 >5 条/秒，每条新消息（即使是其他用户聊天）都触发 header body 整体重算（Text + Capsule + Button + stateBadge）。虽然 cost 不大（无 ForEach），但违反 keep-alive publisher isolation 规则。
