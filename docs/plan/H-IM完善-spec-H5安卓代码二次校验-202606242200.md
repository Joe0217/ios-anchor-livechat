## 1.2 冲突项（已决策）

| 维度 | 决策 | 理由 |
|---|---|---|
| **AGENT_RECHARGE_NOTIFY 编码冲突** | iOS 双形态兜底：数字 99 + 字符串 "AGENT_RECHARGE_NOTIFY" 都识别 | H5 数字 99 / 安卓 字符串 151；I 期接代充时再按后端真值锁定 |
| **NIMChatroomManager vs PartyRoomChatManager 重复** | **H 抽 NIMService 共底座**；两个 ChatroomManager 保留各自 attachType 分发 | NIM 登录态 + 进退房 + delegate 注册三处完全重复，H 是三线（B/E/G）聚合首次集中重构的最自然时机 |
| **GenericCustomAttachmentCoder 注册一致性** | NIMService.setupOnce 统一注册；两个 ChatroomManager 都受益 | 当前派对房没用 coder 是历史遗留，统一后能减分支 |
| **PK data 嵌套 vs 顶层字段** | 维持现状：PKNIMRouter `payload["data"] as? [String:Any] ?? payload` 双兜底 | G 已实测 |
| **心跳频率** | iOS 已锁 10s/>3 次（B 路线图，对齐安卓）| H5 6s/>6 次安卓更严格，已决策对齐安卓 |
| **PK 进度条 clamp** | iOS 采用安卓 `clamp(0.12, 0.88)` 范围限制 | 防止极端比分时进度条被拉爆 |
| **`onSysMsg` 入口** | **H 必须新建 SysMsgRouter**——iOS 当前完全 0 覆盖 | 当前 -3/-4/-6/-1/15/18/35/58/63/64/83/90/103/104 全没接，但 -3/-6/-1/15/18 是 C 通话产品的能力缺口 |
| **`syncSysMsgs` 离线同步** | H 期接入 | 关注累加 / 活动报名补发需要 |
| **礼物动画实现归属** | **属另一会话（礼物全景）**；本会话仅落 `GiftMessageRouter protocol` 钩子 | 用户明确要求 IM 与礼物拆分双会话 |
| **派对房 1004-1112 扩展** | 本会话不做（F 期负责）；NIMService + MessageRouter 框架支持后续加 | 控制 H 范围 |
| **AttachType 是否枚举改 raw Int** | 维持现有 enum 模式（含 unknown(raw:) 兜底），但**case 大幅扩展**；逐一枚举的好处：编译期类型安全 | iOS 现 13 + 15 + PK 6 = 不到 40 个 case，全量约 60-80 个 case 可控；安卓集中 `CustomAttachmentType.kt` 枚举正是这套范式 |
| **错误处理** | 新建 `NIMServiceError` enum，对齐 `APIError` 模式；规则 `error-handling.md` §9 强制 | 当前直播/派对房错误处理不统一 |
