## 三、P1（应该改）

### P1-1 restartForRecording `!session.isRunning` guard 与 suspend 的 sessionQueue.async 存在 race，极限快速 Re-record 会静默失败

- **文件**：[Sources/Register/Camera/RegisterVideoRecorder.swift:186-198](../../Sources/Register/Camera/RegisterVideoRecorder.swift#L186-L198)
- **维度**：concurrency
- **触发链路证据**：
  1. `RegisterVideoRecordView.onDisappear` → `recorder.suspend()` → `camera.stop()` → `sessionQueue.async { session.stopRunning() }`（block A 入队，异步）
  2. Main queue 继续跑：view pop → `onAppear` fire（可能与 block A 未开跑 race）
  3. `onAppear` 检测 `state == .finished` → `Task { await recorder.restartForRecording() }`
  4. `restartForRecording` 里 `if !camera.session.isRunning { camera.start() ... }` guard 检测 `session.isRunning` —— **此时 block A 若还没跑**，`isRunning` 仍是 true → **跳过 camera.start()** + 跳过轮询等待
  5. state 直接置 .ready 返回
  6. 之后 sessionQueue 上 block A 执行 → `session.stopRunning()` → `isRunning=false`
  7. 用户点 Record → recorder.subscribe + timer；但 session 停 → `captureOutput` 不 fire → writer 建不起来
  8. 20s 到 → `stopRecording` → `writerBox nil` guard → `state=.failed(.fileWriteFailed("no video frames captured (writer never built)"))` → `onChange(.failed)` → toast "Recording interrupted. Please retry" + pop
- **复查后判定**：**必修**（P1 而非 P0：需极限快速点 Re-record 才踩；正常 preview 页停留几秒后 block A 已跑完，guard 会正确 restart。但用户报的"Recording interrupted"若还未完全消除，这条 race 是次疑犯）
- **修复**：restartForRecording 里**无条件**调 `camera.start()`（camera.start 自身幂等——sessionQueue.async 内 `if !session.isRunning { startRunning }`）+ 保留轮询等待
  ```swift
  // 无条件调 start；sessionQueue 串行保证 pending stop（若有）完成后 start 排队执行 → stop → start → running
  camera.start()
  let deadline = Date().addingTimeInterval(3)
  while !camera.session.isRunning && Date() < deadline {
      try? await Task.sleep(nanoseconds: 50_000_000)
  }
  guard camera.session.isRunning else {
      state = .failed(.configFailed("session did not restart within 3s"))
      logger.error(...)
      return
  }
  ```
  移除 `if !camera.session.isRunning { ... }` 外层 guard，直接进 start + 轮询逻辑。camera.start 幂等成本 = 一次 sessionQueue.async 派发（若 session 已 running 内部 startRunning 跳）。

### P1-2 RegisterAvatarPickerView `.onChange(of:pickerItem) Task { upload }` 无 epoch 保护，快速切换头像 A→B 若 B 先完成会被后到的 A 覆盖

- **文件**：[Sources/Register/BasicInfo/RegisterAvatarPickerView.swift:32-34](../../Sources/Register/BasicInfo/RegisterAvatarPickerView.swift#L32-L34)
- **维度**：swiftui-perf / correctness
- **触发链路证据**：
  1. 用户第 1 次在 PhotosPicker 选 A 图 → `pickerItem = A` → `Task A { await upload(A) }` 启动
  2. Task A 正在 `ImageUploader.shared.upload(rawData: A_data, preset: .avatar)`（网络 OSS 上传，耗时可能 500ms-数秒）
  3. 用户马上换选 B 图 → `pickerItem = B` → `Task B { await upload(B) }` 启动（Task A 未 cancel）
  4. **B 小 + 网络好** → Task B 先完成 → `store.iconUrl = B_url`
  5. **A 大 + 慢** → Task A 后完成 → `store.iconUrl = A_url` **覆盖 B**
  6. 用户看到显示 A（不是自己最后选的 B），Submit 上传的也是 A
- **复查后判定**：**必修**（现网可复现：4G/弱网下用户"我发现刚才选错了换一张"极常见）
- **修复**：加 epoch guard，类似 [videoCompressEpoch](../../Sources/Register/RegisterStore.swift#L43) 模式
  ```swift
  // store 加：@Published var avatarUploadEpoch: Int = 0
  .onChange(of: pickerItem) { newItem in
      store.avatarUploadEpoch += 1
      let epoch = store.avatarUploadEpoch
      Task {
          guard let item = newItem, let data = try? await item.loadTransferable(type: Data.self) else { return }
          guard epoch == store.avatarUploadEpoch else { return }   // stale 丢弃
          store.isAvatarUploading = true
          defer { store.isAvatarUploading = false }
          do {
              let url = try await ImageUploader.shared.upload(rawData: data, preset: .avatar)
              guard epoch == store.avatarUploadEpoch else { return }
              store.iconUrl = url
              store.avatarUploadError = nil
          } catch { ... }
      }
  }
  ```
  或者更简单：保留 currentTask 引用，next Task 前 cancel 前一个。

## 四、P2（可以改）

### P2-1 RegisterVideoPreviewView.upload 在 @MainActor 里同步 Data(contentsOf:) 读 5-6MB mp4 阻塞 main 100+ms

- **文件**：[Sources/Register/Camera/RegisterVideoPreviewView.swift:107-108](../../Sources/Register/Camera/RegisterVideoPreviewView.swift#L107-L108)
- **维度**：swiftui-perf
- **触发链路证据**：用户点 Upload 按钮 → `Task { await upload() }` → `Data(contentsOf: compressedUrl)` 同步磁盘 IO 读 5-6MB 到内存 → main queue 阻塞。视觉上"Upload 按钮 spinner 出现前的 100+ms 卡顿"。
- **复查后判定**：**信息**（真机 iPhone 12+ SSD 快，实测可能 <50ms 不明显；旧机型或热限流下可能感知）
- **建议**：`Data(contentsOf:)` 移到 Task.detached 或用 async File API
  ```swift
  let data = try await Task.detached(priority: .userInitiated) {
      try Data(contentsOf: compressedUrl)
  }.value
  ```

### P2-2 RegisterVideoRecorder.stopRecording writer.finishWriting completion 内 strong self 捕获

- **文件**：[Sources/Register/Camera/RegisterVideoRecorder.swift:239-252](../../Sources/Register/Camera/RegisterVideoRecorder.swift#L239-L252)
- **维度**：memory
- **触发链路证据**：`box.writer.finishWriting { Task { @MainActor in self.state = ...; self.writerBox = nil } }` closure 未 `[weak self]`。理论上：writer 卡住不 fire completion → self 永生 → CameraManager 永生 → 摄像头灯不熄。产品链路无真触发：AVAssetWriter.finishWriting 官方保证一定 fire completion；且用户 flow 结束后 @StateObject.deinit 触发 camera.tearDown 即使 self 泄漏也不影响 session 关停（session 是 CameraManager 的 let，CameraManager dealloc 时 session dealloc → session 自动 stop）。
- **复查后判定**：**信息**（防御性优化，无产品可触发）
- **建议**：改 `[weak self]`

### P2-3 CameraManager.tearDown 从非 main queue 触发时对 @Published 字段的写会 SwiftUI publish warning

- **文件**：[Sources/Camera/CameraManager.swift:362-374](../../Sources/Camera/CameraManager.swift#L362-L374)
- **维度**：swiftui-perf
- **触发链路证据**：RegisterVideoRecorder.deinit 是 nonisolated（Swift 5 语义），触发 `camera.tearDown()` 时可能在 arbitrary queue。tearDown 内部 `stopInterruptionTracking()` 写 `interruptionUnrecoveredDuration = 0`（@Published）→ 若非 main queue → SwiftUI "Publishing changes from background threads is not allowed" warning。**本轮本轮新 deinit 引入的**（其他 caller 如 LiveRoomView.onDisappear 走 main queue，无此问题）。
- **复查后判定**：**信息**（现有 CameraManager 设计问题，本轮 register deinit 触发概率低——ARC dealloc 大概率在 main queue，但 nonisolated deinit 不保证）
- **建议**：CameraManager.tearDown 内部对 @Published 的写包 `DispatchQueue.main.async { }` 或 `Task { @MainActor in ... }`；本轮 register 侧的兜底：Recorder.deinit 里 `Task { @MainActor in self.camera.tearDown() }` 强制 main queue（但 deinit 里跨 actor Task 复杂，Swift 6 有 isolated deinit 才干净）

### P2-4 SessionStore.resubmit path 若用户中途 back 到 LoginView 根 + kill app，Keychain 里 pendingRegisterPassword 明文残留（无 TTL）

- **文件**：[Sources/Auth/SessionStore.swift:120-121](../../Sources/Auth/SessionStore.swift#L120-L121)
- **维度**：security
- **触发链路证据**：用户走 resubmit login 成功 → AuthToken.value 临时授权 + Keychain.setString(pwd, .pendingRegisterPassword) → 用户 back 离开注册流不 submit → kill app。冷启动时 SessionStore.load 无 user → 走 LoginView 常规登录；**pendingRegisterPassword 残留在 Keychain**（只有下次 login 1005 catch 或 resubmit path 才会重新覆盖 / 或 submit 成功 + logout 才会 remove）。
- **复查后判定**：**信息**（Keychain 用户级 encrypted at rest；残留是 dead data，即使外泄仍需设备解锁 + 越狱；且明文密码用户已在 LoginView 输入过，同源）
- **建议**：冷启动 SessionStore.init/load 里若无 user，主动 `KeychainStore.remove(for: KeychainKey.pendingRegisterPassword)` 清 dead data。成本 = 1 行代码。
