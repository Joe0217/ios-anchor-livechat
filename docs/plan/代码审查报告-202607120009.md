## 二、必修

### P1-1 `PartyListStore.currentTask` 生命周期串扰导致下拉刷新 spinner 一闪即收（loadMore 后场景）

- **文件**：[Sources/Party/List/PartyListStore.swift:145-169, 275-283](../../Sources/Party/List/PartyListStore.swift)
- **维度**：并发 / 状态机
- **触发场景 + 概率**：
  - 用户操作序列：**下拉刷新完成 → 触底加载更多 → 再下拉刷新**
  - 真机 100% 复现（loadMore 后必然进 inflight guard 分支）
  - 产品调用链路证据：
    - `PartyRoomListContent.loadMoreSentinel.onAppear` → `store.loadMore()` → `beginLoadMore` → `currentTask = Task { performLoadMore(...) }`
    - `beginLoadMore` **不清** `currentTask = nil`（对比 refreshAsync L168 有清）
    - 用户下拉 → `.refreshable { await refreshAsync() }` → inflight guard `if let existing = currentTask { await existing.value; return }` → **existing 是已完成的 loadMore task**，`.value` 立即返回 → refreshAsync 提前 return，state 未迁移到 `.refreshing`，SwiftUI spinner 立即收起
- **风险**：与用户 2026-07-11 反悔的"下拉释放前 spinner 就缩回"是**同源问题的新场景**。当时修了 refreshAsync 自身完成后清 nil，但 beginLoadMore + beginRefresh 都没清 → loadMore 完成后 currentTask 变成"看似 inflight 实则已完成"的僵尸引用
- **严重度**：中（不会崩溃 / 数据损坏，但下拉刷新 UX 断裂）
- **建议修复**：
  ```swift
  // 方案：加 isRefreshing flag 与 currentTask 解耦；refreshAsync 只 gate 自己
  private var isRefreshing = false

  func refreshAsync() async {
      if isRefreshing {
          await currentTask?.value  // 等已在跑的 refresh
          return
      }
      isRefreshing = true
      defer { isRefreshing = false }
      // ... 原状态机 + task.detached
  }
  ```
  或者在 `beginLoadMore` / `beginRefresh` 里给 Task closure 结尾清 `currentTask = nil`（对齐 refreshAsync L168 模式）。**推荐方案 A**：语义更清晰（refresh inflight vs loadMore 是两条独立生命周期）
