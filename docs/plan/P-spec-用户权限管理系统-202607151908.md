# 用户权限管理系统 · Spec

> 版本 v1 · 2026-07-15 · 跨模块（Call / Match / Live / Party）· A 档

## §0 目标与范围

### 0.1 目标

在项目里落地一套**账户级硬性权限系统**：根据登录用户的 `userType` 判定当前主播能否使用 4 大核心功能（通话 / 匹配 / 直播 / Party 房），从 UI 入口到 Store 发起到 IM/RTM 呼入三层同步阻断。

### 0.2 范围三圈

| 圈 | 内容 |
|---|---|
| 核心 | `SelfPermissionBridge` 数据源 + 4 大功能三层防护 gate（UI 隐藏 / Store guard / RTM 呼入 auto-reject） |
| 依赖已就绪 | `SessionStore.user`（@Published，含 `userType`）· `AppLogger.call`（日志）· `CallStore.callOut / RTM videoCall handler`（现有）· `CallAuthBridge`（保留不动） |
| 占位 | Party P2P 邀请函 attachType 1002 handler（iOS 未实装）—— 本 spec 只标 TODO，未来接入 1002 时同步 gate |

### 0.3 决策与来源锁定

| 决策项 | 结论 | 来源 |
|---|---|---|
| userType 黑名单值域 | 101-106 六种硬编码，H5/安卓蓝本**无对应** | 用户明示 |
| 通话 + 匹配 bit 合并 | 合成一个 `.call` bit（矩阵里 101/104/105 都同时屏两者） | 用户明示 |
| 与 CallAuthBridge 段位判定关系 | **两套独立、不冲突**；段位仅影响 LiveList / UserProfile / ChatDetail **UI 显示**，userType 是全局三层硬 gate | 用户明示 |
| 配置源 | 硬编码 iOS 端，不走 AppConfig 下发 | 用户明示 |
| Party 被动接收阻断 | 现阶段 iOS 未接 attachType 1002 → spec 只标 TODO，不实装 handler | 用户明示 |
| 性能约束 | 单例 shared bridge + removeDuplicates + OptionSet；禁止每 view 独立订阅 | 用户明示 |

## §2 数据模型与状态机

### 2.1 `BlockedFeatures` OptionSet

```swift
/// 权限受限功能的 3 bit 组合。call 位同时代表"通话 + 匹配"（两者绑定）。
struct BlockedFeatures: OptionSet {
    let rawValue: Int
    static let call  = BlockedFeatures(rawValue: 1 << 0)  // 通话 + 匹配
    static let live  = BlockedFeatures(rawValue: 1 << 1)  // 直播
    static let party = BlockedFeatures(rawValue: 1 << 2)  // Party 房
}
```

### 2.2 `userType → BlockedFeatures` 硬编码映射

```swift
enum UserPermissionMapping {
    /// 未知/未受限 userType（含 2/9/nil/其他）返回 `[]`（不屏蔽任何功能）。
    static func blocked(for userType: Int?) -> BlockedFeatures {
        switch userType {
        case 101: return [.call]
        case 102: return [.live]
        case 103: return [.party]
        case 104: return [.call, .live]
        case 105: return [.call, .party]
        case 106: return [.live, .party]
        default:  return []
        }
    }
}
```

**为何硬编码**：用户明示不走 AppConfig 下发；spec §11 保留"未来若产品要动态调整"的扩展路径。

### 2.3 `SelfPermissionBridge`（单例 shared，性能优先）

```swift
final class SelfPermissionBridge: ObservableObject, @unchecked Sendable {
    static let shared = SelfPermissionBridge()

    // MARK: - UI 层订阅（@MainActor · SwiftUI 主线程读）
    @MainActor @Published private(set) var canCall: Bool = false
    @MainActor @Published private(set) var canLive: Bool = false
    @MainActor @Published private(set) var canParty: Bool = false
    @MainActor @Published private(set) var isLoaded: Bool = false

    // MARK: - Store 层 nonisolated snapshot（原子读，避免 @MainActor hop）
    private let snapshotLock = NSLock()
    private var _snapshot: BlockedFeatures = []
    private var _isLoaded: Bool = false

    /// **Store guard 专用**：nonisolated 原子快照读，各 store 从任意 actor 调 `SelfPermissionBridge.shared.canCallSnapshot` 均安全。
    /// UI 层继续读 `$canCall @MainActor @Published`（Bridge 内部同步双写）。
    nonisolated var canCallSnapshot: Bool {
        snapshotLock.lock(); defer { snapshotLock.unlock() }
        return _isLoaded && !_snapshot.contains(.call)
    }
    nonisolated var canLiveSnapshot: Bool {
        snapshotLock.lock(); defer { snapshotLock.unlock() }
        return _isLoaded && !_snapshot.contains(.live)
    }
    nonisolated var canPartySnapshot: Bool {
        snapshotLock.lock(); defer { snapshotLock.unlock() }
        return _isLoaded && !_snapshot.contains(.party)
    }

    init(session: SessionStore = .shared) {
        // userType 变化才重算 —— removeDuplicates 拦截无关字段变化
        let userTypePublisher = session.$user
            .map { $0?.userType }
            .removeDuplicates()

        let blockedPublisher = userTypePublisher
            .map { UserPermissionMapping.blocked(for: $0) }
            .share() // 多订阅共享上游

        // 一次 sink 双写 —— 更新 snapshot lock 保护的态 + @MainActor @Published
        blockedPublisher
            .combineLatest(session.$user.map { $0 != nil }.removeDuplicates())
            .removeDuplicates(by: { $0.0 == $1.0 && $0.1 == $1.1 })
            .sink { [weak self] blocked, loaded in
                guard let self else { return }
                self.snapshotLock.lock()
                self._snapshot = blocked
                self._isLoaded = loaded
                self.snapshotLock.unlock()
                // MainActor 侧同步 @Published（UI 订阅）
                Task { @MainActor in
                    self.canCall  = loaded && !blocked.contains(.call)
                    self.canLive  = loaded && !blocked.contains(.live)
                    self.canParty = loaded && !blocked.contains(.party)
                    self.isLoaded = loaded
                }
            }
            .store(in: &cancellables)
    }

    private var cancellables = Set<AnyCancellable>()
}
```

**双 API 语义**（回应 spec-review Finding 1）：
- UI 层（SwiftUI view / @MainActor 上下文）读 `$canCall @Published` —— 声明式响应变化
- Store 层（非 @MainActor async 方法）读 `canCallSnapshot` nonisolated —— 原子读无 hop
- **不变量**：snapshot 与 @Published 由同一 sink 同步双写（无时序漂移；MainActor.Task 微秒级延迟 UI 可接受）

**关键设计约束**（用户明示"避免性能问题"）：
- 单例 `shared` —— 全项目一个订阅链，各 view 只读派生 @Published 属性
- `removeDuplicates` 三层拦截（userType → blocked → canX），无 userType 变化时 view body 不重算
- `BlockedFeatures` 是 Int rawValue OptionSet，`contains(.call)` 是位运算 O(1)
- 禁止在 view 里 `@StateObject SelfPermissionBridge()` new 独立实例 —— 全用 `.shared`

### 2.4 判定优先级

| 判定 | 数据流 | 消费者 |
|---|---|---|
| **userType 全局硬 gate** | `SelfPermissionBridge.shared.canX` | 所有三层（UI / Store / RTM）· 全 4 功能域 |
| **段位显示 gate**（H5 anchortCallAuth 语义） | `CallAuthBridge.shared.canCall` | 仅 LiveList / UserProfile / ChatDetail **UI 按钮显示** |

**组合规则**（LiveList / UserProfile / ChatDetail UI 按钮显示 3 处）：
```
showCallBtn = SelfPermissionBridge.shared.canCall && CallAuthBridge.shared.canCall
```

**其他消费点**（CallStore / RTM 呼入 / Match / Live / Party）：只看 `SelfPermissionBridge.shared.canX`（UI 层）或 `.canXSnapshot`（Store 层），不引入段位。

**命名约定**（回应 spec-review Finding 6）：spec 全文以下三种写法等价，语境使用：
- `SelfPermissionBridge.shared.canX` —— UI @MainActor 上下文 @Published 订阅
- `SelfPermissionBridge.shared.canXSnapshot` —— Store 非 @MainActor async 方法 nonisolated 读
- 简写 `permission.canX` / `permission.canXSnapshot` —— 上下文可推导 `permission` 别名时使用

#### 3.1.1 Party tab 动态渲染 · selection 兜底（回应 spec-review Finding 2）

Party tab 4 → 3 动态变化涉及 SwiftUI TabView tag 运行时消失，需**显式处理 selection 恢复态**（否则 SwiftUI 会 fallback 首 tab 或触发异常动画）。

**规则**：
- 若 `permission.canParty == false`：
  - `MainTabView.body` **不渲染** `.tabItem` 里的 party 分支（tab bar 只剩 3 个 icon）
  - 若当前 `selection == .party`（切账号/上次持久化态）→ **主动 fallback 到 `.home`**，写入前先 `partyPath = NavigationPath()` 清路径
  - 若持久化 `@AppStorage/@SceneStorage` 的 selection 值是 .party → 读取时 `guard permission.canPartySnapshot` 通过否则回退到 `.home`
- 若 `permission.canParty == true → false` 运行时转变（如 SessionStore.user.userType 更新触发）：
  - `MainTabView` 需订阅 `permission.$canParty` sink，`false` 到达时若 `selection == .party` 立即 fallback（同上）

**实施位置**：
- `MainTabView.swift:selection` 计算属性引入 permission guard
- `MainTabView.swift:body` `.tabItem` party 分支包 `if permission.canParty { ... }`
- 补一处 `.onChange(of: permission.canParty) { ... }` 处理运行时变化

**已知风险**：SwiftUI TabView 在 tab 数量变化时可能触发子 view dismantle + 重建（含 Party 子树 dismount），需真机验证冷启动 / 切账号 / 运行时 revoke 三种场景。**若真机发现闪烁 / 状态丢失严重，回退方案**：Party tab 保留 `.tabItem`，`PartyTabRootView` 内容体判 `permission.canParty` 后渲染空态 + 提示"该账户暂无 Party 权限"（视觉降级但结构稳定）。

**guard 失败行为**：`AppLogger.call/live/party.info` 记录 + 无 toast（避免越界；spec §7 已知留白）。若产品要求 toast，加统一 `LivePermissionToastBus` 单例（本 spec 不含）。

**Store isolation 与 guard 调用点约束**（回应 spec-review Finding 1）：
- 5 个 gate method 现状均为 `func xxx() async` 无 @MainActor 标注：
  - `CallStore.callOut(remoteUserId:) async` [CallStore.swift:514]
  - `MatchStore.openMatch() async` [MatchStore.swift:289]
  - `LiveSettingsStore.startTapped() async` [LiveSettingsStore.swift:122]
  - `PartyTabRootView.tapCreate()` [PartyTabRootView.swift:134] · `PartyStore.enterRoom(roomId:password:) async` [PartyStore.swift:210]
- **调用约定**（回应 spec-review N3 放宽）：
  - **async 非 @MainActor method**（`CallStore.callOut` / `MatchStore.openMatch` / `LiveSettingsStore.startTapped` / `PartyStore.enterRoom`）**一律用 `.canXSnapshot`** —— 跨 actor read `.canX @MainActor` 编译错 / Swift 5 静默 UB
  - **@MainActor View method**（`PartyTabRootView.tapCreate` 是 SwiftUI View 内 private func，默认 @MainActor 隔离）**可以直接用 `.canX @Published`** —— 已在 main actor 无需 hop，snapshot 是冗余保险
  - 判断规则：method 声明含 `async` 且未显式 `@MainActor` → 用 snapshot；纯 View 内 sync method → 用 @Published
- 例（CallStore.callOut 开头）：
  ```swift
  func callOut(remoteUserId: String) async {
      guard SelfPermissionBridge.shared.canCallSnapshot else {
          AppLogger.call.info("[Permission] callOut blocked by userType gate")
          #if DEBUG
          assertionFailure("callOut called while permission.canCall == false — 应在 UI 层拦截")
          #endif
          return
      }
      // ... existing logic
  }
  ```

**失败反馈一致性**（回应 Finding 8）：DEBUG build `assertionFailure` 提示"应在 UI 层拦截"（能到 Store guard = UI 侧漏 gate = 开发期 bug），Release build 静默 return + log。绕过 UI 直调场景在 dev 期主动暴露，生产则安全静默 —— 避免用户感知权限受限状态（安全侧）+ dev 期不漏隐性入口。

### 3.3 IM/RTM 被动接收阻断层

| 通道 | 阻断点 | 行为 |
|---|---|---|
| RTM `videoCall` 呼入（含普通通话 + matchV4 派单） | `CallStore` `handleIncomingVideoCall(msg)` [Sources/Call/CallStore.swift:1236] 入口 | `guard SelfPermissionBridge.shared.canCall else { await sendReject(msg); return }` |
| Party 邀请函 attachType 1002 | **N/A**（iOS 未实装 handler） | **spec TODO**：未来接 1002 时同步在 handler 开头 `guard canParty else return`；本 spec 不实装 |
| Match IM 派单 | 无独立 IM，走 RTM videoCall 同一通道 | 已被 RTM 通道阻断覆盖 |
| Live 被动接收 | 无（直播只主动发起） | N/A |

**关键**：Match 到人自动 accept 的判定链是 `CallStore.handleIncomingVideoCall` → `source == "matchV4"` → `accept(auto:true)` [CallStore.swift:1381-1385]。只要在 `handleIncomingVideoCall` 入口拒接，match 派单同步被拒。**无需在 MatchStore 层再加拒接分支**。

**RTM 阻断层覆盖细节**（回应 spec-review Finding 3）：
- **voiceCall 通道**：项目决策"音频通话/虚拟来电不做"（[CLAUDE.md] §已知坑相邻决策）+ 全项目 grep `voiceCall` 无相关代码 → **不存在需覆盖的 voiceCall RTM 通道**
- **source 值域**：全项目 grep `source ==` 只找到 `matchV4` 一种识别码；`handleIncomingVideoCall` 入口 guard 在 source 判定**之前**，天然覆盖所有 source（matchV4 / 未来新增 direct / quick / etc.）
- **SystemMessageRouter**：项目内 SystemMessageRouter 派发 IM sysMsg（礼物特效 / 警告 / 封禁 / 排行榜等），**不直接触发通话**；通话入口是 CallStore RTM 通道，与 SystemMessageRouter 正交 → **不需在 SystemMessageRouter 层加 gate**

### F-20 RTM 呼入层

- **F-20**: userType=101 主播收到 RTM `videoCall` 呼入 → 立即 `sendReject`，`CallStore.state` 保持 `.idle`，主叫方感知为 reject
- **F-21**: userType=101 主播收到 matchV4 派单（RTM `videoCall` + `source=matchV4`） → 同 F-20 拒接，MatchStore 不进入 `.matchingCalling`
- **F-22**: userType=104 主播收到 RTM `videoCall` → 拒接（call bit 命中即拒，无论其他 bit）

### R-* 反向验收

- **R-1**: userType 从 2 → 101 且**当前正在通话中** → 正在的会话**不主动挂断**（本 spec 不 handle 会话内实时 revoke；已挂断/下一次呼入才生效）
- **R-2**: userType 从 101 → 2 → 按钮/入口立即恢复（Bridge removeDuplicates 拦截后仍触发 UI 重算）
- **R-3**: userType 未知值（如 200 / 50 / 9999） → 视为不屏蔽（default: `[]`）
- **R-4**: SessionStore user nil（未登录） → 应用不到本层（无 tab 可用），但 Bridge 状态为 isLoaded=false / 所有 canX=false
- **R-5**: 段位命中 + userType 命中黑名单 → LiveList 按钮隐藏（AND fail 于 userType）
- **R-6**: 段位不命中 + userType 不命中 → LiveList/UserProfile/ChatDetail 按钮隐藏（AND fail 于段位），符合现有 H5 anchortCallAuth 行为
- **R-7**: RTM 呼入被自动拒时，主叫方感知 = 常规 reject 信令，不区分原因（避免暴露主播权限受限状态）
- **R-8**: 权限系统 Bridge 未初始化 / SessionStore.user 未 load → isLoaded=false → 所有 UI 层按钮 hidden（对齐 async-state-fallback rule）
- **R-9**: userType == 104 主播 tap `LiveSettingsStore.startTapped()` → 现有 load() userType != 2 gate 已拦，本 spec startTapped guard 是冗余保险
- **R-10**: Party tab 完全不渲染时，路由到 `.party` tab 的深链（若有）应 fallback 到 home tab（`MainTabView.selection` 兜底，详见 §3.1.1）
- **R-11**（新增 · Finding 7）：ToolsSection [ToolsSection.swift:61-70] 开播入口 —— userType=102 时 gate 通过（导航链断），Work tab 深链跳 firstLiveRule 应也 fallback 首页
- **R-12**（新增 · Finding 7）：`PartyListMainView` 房间列表 cell 点击 —— userType=103 时点击 gate 拦截，AppLogger 记录，不 append PartyRoute（等价于 R-10 party path 阻断）
- **R-13**（新增 · Finding 7）：`LiveTabView` `.match` outer tab 展开时 `floatingButtons(for:)` [LiveTabView.swift:215-220] —— userType=101 时 CGoMatchButton 完全不渲染（float 层空）
- **R-14**（新增 · Finding 2）：Party tab 运行时 revoke —— `selection == .party` 时 `permission.canParty` false 到达，`.onChange` sink 立即 fallback `.home` + 清 partyPath；真机验证不触发 crash / 异常动画
- **R-15**（新增 · Finding 2）：Party tab 冷启动 —— `@SceneStorage("mainTabSelection")` 值为 `.party` 但 permission 未加载完 → `selection` 兜底逻辑：等 permission.isLoaded 后判定；未 load 期 fallback `.home`

## §6 兜底策略

- **未加载态**（Bridge 未订阅到 SessionStore.user）→ 所有 canX=false，UI 全隐
- **未知 userType**（如未来后端加 107/108 未在 iOS 硬编码表内）→ default `[]`，不屏蔽；等 iOS 下版本更新映射表
- **网络异常导致 SessionStore.user 短暂 nil**（很少见，logout 才 nil）→ 一律视为未登录，UI 应回归登录页，本 spec 不额外处理
- **AppLogger.party 若不存在** → 用 `AppLogger.live` 代替；若要新增在 [AppLogger.swift] 补 category

### 6.1 Deny-by-default 决策（回应 spec-review Finding 5）

Bridge 未加载态 `canX=false` 与 [async-state-fallback](../.claude/rules/async-state-fallback.md) rule "loading 占位是 dead-state 反模式"看似冲突，实为**权限系统的安全约定 fail-safe defaults**：

- **异步兜底 rule 语境**：业务 UI 派生（如 tab 顺序、UI 主题）应有"业务可用兜底值立即渲染"，避免 loading 占位卡死。**未加载态给"最常见业务值"是乐观兜底**。
- **权限系统语境**：账户级硬性权限（涉及运营/风控/合规）**必须 deny-by-default**（fail-safe defaults）—— 未确认账户身份就允许敏感操作是安全反模式。业界共识（OWASP / Apple Security Doc）。
- **实测 flash 时长**：SessionStore.user 在 `login()` 完成瞬间同步可用（[SessionStore.swift:139] applyLogin 内），Bridge 订阅 sink 到达 <10ms；冷启动持久化 token 场景 SessionStore.applyStoredIfNeeded 也是同步。**实测 flash <100ms**，UI 通过 `permission.isLoaded == false` 隐藏所有 gate 入口 → 用户视觉 = 页面组件"渐次出现"（正常加载感），非"闪一下消失"。
- **明确接受**：此 flash 是权限系统安全属性的合理代价，不采用"乐观兜底"（该 rule 不适用于权限判定语境）。若真机发现明显 flash，通过 `SessionStore.applyStoredIfNeeded` 前置加载优化，而非改变 deny-by-default 语义。
