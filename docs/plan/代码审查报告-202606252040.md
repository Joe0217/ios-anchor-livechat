## 二、P0（必须改）

### P0-1 NIMService NIMSDK delegate 未标 `nonisolated`

- **文件**：[Sources/Live/NIM/NIMService.swift:295-341](../../Sources/Live/NIM/NIMService.swift#L295-L341)
- **维度**：Swift 并发
- **风险**：`NIMService` 类整体 `@MainActor`，但 `onReceive` / `onLogin` / `onKickout` / `onAutoLoginFailed` 都直接写成成员方法（继承类的 MainActor 隔离），未加 `nonisolated`。NIMSDK 的 Obj-C delegate 回调来自 SDK 内部线程，调 `@MainActor` 方法会触发 Swift runtime actor 隔离违规。同模块兄弟类 `NIMChatroomManager (L175/L183)` 和 `PartyRoomChatManager (L261/L273)` 都正确加了 `nonisolated`——是漏标。一旦命中 `onKickout`（1004 挤下线）/ `onAutoLoginFailed`（1005 token 失效）会让 `.apiSessionInvalidated` 广播路径直接崩，或访问 `self.connectionState` `@Published` 字段命中 UI thread checker。
- **修复**：四个 delegate 方法前加 `nonisolated`：

  ```swift
  nonisolated func onReceive(_ notification: NIMCustomSystemNotification) {
      Task { @MainActor in
          self.dispatchSystemNotification(notification, context: .sysMsg)
      }
  }
  ```

  `onLogin` / `onKickout` / `onAutoLoginFailed` 同样处理。方法体已 `Task @MainActor` 切回主 actor，行为不变。

## 三、P1（应该改）

### P1-1 `CallFaceTimeView` 即使复用 `liveCamera` 仍会预实例化 `fallbackCamera`

- **文件**：[Sources/Call/CallView.swift:119-125](../../Sources/Call/CallView.swift#L119-L125)
- **维度**：内存与资源
- **风险**：`@StateObject private var fallbackCamera = CameraManager()` 与 `@StateObject private var fallbackBeauty = BeautyParameters()` 是 `@StateObject` 默认值——SwiftUI 在 View 实例化时**立即调用** `CameraManager()` 构造器，不论 `liveCamera` 是否为 nil。直播私 call 路径 `liveCamera` 由 `LiveRoomView` 注入永不为 nil，但仍会在 `CallFaceTimeView` 出现的瞬间额外创建一个 `CameraManager` 实例 → 构造 `AVCaptureSession` + Metal renderer + 美颜资源（FURenderKit 单实例 100MB+）。虽未启动 `startRunning()` 但 init 阶段已申请 GL/Metal context；该 `fallbackCamera` 由 `@StateObject` 持有直到 view 销毁，等于通话期间常驻一份"幽灵"美颜管线，直接增加 OOM 风险（热启 + 弱网下播路径）。
- **修复**：用 lazy 模式，按需创建：

  ```swift
  @StateObject private var fallbackHolder = CallFaceTimeFallbackHolder()
  private var camera: CameraManager {
      liveCamera ?? fallbackHolder.lazyCamera
  }
  ```

  其中 `CallFaceTimeFallbackHolder` 内 `var lazyCamera: CameraManager { ... }` 用 lazy 初始化；或拆两个子 View（`CallFaceTimeViewWithLive` vs `CallFaceTimeViewStandalone`）分别走不同路径。

### P1-2 `Timer.publish` 在 View 内驱动通话计时——违反 `.claude/rules` 收敛进 Store

- **文件**：[Sources/Call/CallView.swift:54,80-85,122,166-168](../../Sources/Call/CallView.swift#L54)
- **维度**：SwiftUI 性能
- **风险**：`CallWaitingView` 与 `CallFaceTimeView` 各自把 `Timer.publish(every: 1, on: .main, in: .common).autoconnect()` 作为 struct 成员存储。每次 SwiftUI 重算 View（父 ZStack 在 store 频繁刷新如 sysMsg HUD 字段变化时反复 re-eval），struct 值类型字段会被重新生成新的 Combine publisher，`.autoconnect()` 立刻起新订阅——旧 timer 释放有滞后，存在多 timer 并发同时 tick 风险（elapsed 重复递增 / 倒计时跳秒）。更严重的是 CLAUDE.md + `.claude/rules` 明确要求"副作用（计时器/心跳/强制下播）全收敛进 Store/Controller"，直播侧 `LiveTimerStore` 已对齐该模式，通话侧反规范。
- **修复**：把 `elapsed` 移到 `CallStore`：新增 `@Published private(set) var callOutElapsed: Int` 与 `callConnectedElapsed: Int`，由 CallStore 内部一个 `Task @MainActor` with `Task.sleep` 驱动，state 切换时 cancel/restart（参考 `LiveTimerStore` 与 `endedToIdleTask` 模式）。`CallWaitingView` / `CallFaceTimeView` 改为 `@ObservedObject` 读 store 字段，移除 `tickTimer` / `@State elapsed` / `onReceive`。

### P1-4 `NIMService.setupOnce` SDK 注册在锁外，并发第二者读到 `didSetup=true` 即 return

- **文件**：[Sources/Live/NIM/NIMService.swift:58-85](../../Sources/Live/NIM/NIMService.swift#L58-L85)
- **维度**：Swift 并发
- **风险**：`didSetup = true` 在加锁段内置位，但 `NIMSDK.shared().register(with:)` + `registerCustomDecoder` + `Task delegate.add` 全在解锁后执行。两线程并发进 `setupOnce` 时第二者立即见 `didSetup==true` 直接 return，此时第一者还没跑完 `NIMSDK register`。第二者随即 `NIMService.shared.login` 走 `NIMSDK.shared().loginManager.login`，命中 SDK 未注册 appKey 窗口期，导致 login 静默失败（errorCode=400 / 参数错），**首次冷启动登录概率性失败**。`HilyApp.init` / `NIMChatroomManager.enter` / `NIMOnlineKeeper.start` 三处都调 `setupOnce`，并发概率不可忽略。

  ```swift
  nonisolated static func setupOnce() {
      didSetupLock.lock()
      defer { didSetupLock.unlock() }
      if didSetup { return }
      NIMSDK.shared().register(with: option)
      NIMCustomObject.registerCustomDecoder(GenericCustomAttachmentCoder())
      didSetup = true
      Task { @MainActor in /* delegate.add */ }
  }
  ```

### P1-6 `PartyRoomChatManager` 缺 `deinit` 注销 NIMSDK delegate

- **文件**：[Sources/Party/Chat/PartyRoomChatManager.swift:33-35](../../Sources/Party/Chat/PartyRoomChatManager.swift#L33-L35)

### P2-8 `NIMChatroomManager.enter` 重复调用会重复 add delegate

- **文件**：[Sources/Live/NIMChatroomManager.swift:39-68](../../Sources/Live/NIMChatroomManager.swift#L39-L68)
- **维度**：内存与资源
- **风险**：`enter()` 无 `hasJoined` 守卫（对比 [PartyRoomChatManager.swift:53-57](../../Sources/Party/Chat/PartyRoomChatManager.swift#L53-L57) 有 `guard !hasJoined`）。若 LiveRoomView 在某些 SwiftUI 重 `makeUIView` 路径或 `onAppear` 二次触发场景下再次调用 `enter()`，NIMSDK 会把同一个 manager 实例 add 两次到 delegate 数组——NIMSDK_LITE 10.10.0 实现是 `NSHashTable` 经验上能去重，但官方文档不保证，同一条 `onRecvMessages` 会被 `processIncoming` 触发两次 → **公屏消息重复 + onlineCount 翻倍 + 礼物动画双播**。
- **修复**：加 `hasJoined` 守卫（对齐 PartyRoomChatManager）：

  ```swift
  private var hasJoined = false
  func enter(roomId: String, nickname: String) {
      guard !hasJoined else {
          AppLogger.im.notice("[Chatroom] already joined room=\(self.roomId), skip")
          return
      }
      ...
      // 进房成功回调内 self.hasJoined = true
  }
  func leave() {
      guard !roomId.isEmpty else { return }
      hasJoined = false
      ...
  }
  ```

### P2-9 `NIMOnlineKeeper.start/stop` Task 无串行化，快速切账号下 `isLogined` 错位

- **文件**：[Sources/Live/NIMOnlineKeeper.swift:22-51](../../Sources/Live/NIMOnlineKeeper.swift#L22-L51)
- **维度**：Swift 并发
- **风险**：`start/stop` 各自 `Task @MainActor` fire-and-forget。SessionStore 快速登出/重登场景（token 失效自动重登）短时 `stop()→start()`：两 Task 在主 actor FIFO 各自 await 让出，logout Task 内部 SDK 完成前 start Task 已跑到 await login，最后 `connectionState` 顺序错乱（logout 后写 `.idle` 覆盖新 login 的 `.connecting`/`.connected`）。表象：**秒级切账号后主播在线态对端短时看不到**。
- **修复**：引入 `pendingTask: Task<Void,Never>?` 串行：每次 `start/stop` 先 `_ = await prior?.value` 再做实际工作；或改 actor。

### P2-10 PartyRouter 把整个 ext 字典以 public 打日志

- **文件**：[Sources/Party/NIM/PartyMessageRouter.swift:76](../../Sources/Party/NIM/PartyMessageRouter.swift#L76)
- **维度**：安全与隐私
- **风险**：1012 `seatUpdateList` 消息的 `remoteExt` 在派对房内会带 `userId / nickname / yxAccid / roomTempId` 等多个业务字段，用 `privacy: .public` 整 dump 后 Console / sysdiagnose / 用户上传崩溃日志都会落明文。任何走过派对房的用户的 ID/昵称都可能从此日志路径泄漏。L118 / L122 已经对 `myUid` 和 `roomId` 用了 `.private`，唯独 1012 通道整 ext 漏了。
- **修复**：只打 keys 不打 value，或整体改 `.private`：

  ```swift
  AppLogger.party.notice("[PartyRouter] 1012 keys=\(Array(ext.keys), privacy: .public)")
  ```

  如果排查需要 value，加 `#if DEBUG` 保护。
