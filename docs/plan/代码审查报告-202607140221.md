## 四、P2（归档，用户仅要求"应修的都修" = P1 已 0；P2 归入 J 里程碑 backlog）

### P2-1 RegisterVideoRecorder.deinit 在非 main queue 触发时 CameraManager.tearDown 写 @Published 触发 SwiftUI publish warning

- **文件**：[Sources/Camera/CameraManager.swift:362-374](../../Sources/Camera/CameraManager.swift#L362-L374) + [Sources/Register/Camera/RegisterVideoRecorder.swift:38](../../Sources/Register/Camera/RegisterVideoRecorder.swift#L38)
- **维度**：swiftui-perf
- **产品链路证据**：`RegisterVideoRecorder` 是 `@MainActor final class`，Swift 5 里 deinit 是 nonisolated；ARC 可能在 arbitrary queue 释放。deinit 内 `camera.tearDown()` → `stopInterruptionTracking()` → 写 `interruptionUnrecoveredDuration = 0`（`@Published`）→ 若非 main queue → warning。**实际大多数场景**：@StateObject 释放在 main queue，warning 不触发
- **复查后判定**：**信息**（上一轮报告已归档为 P2-3；CameraManager 现有设计问题非本轮引入）
- **建议**：留 J 里程碑收尾时对 CameraManager.tearDown 内部 @Published 写包 `DispatchQueue.main.async {}`

### P2-2 Multiple showToast Task race — 2s 内多次 error 会让早启动的 Task clear 新 toast

- **文件**：[Sources/Register/Camera/RegisterVideoPreviewView.swift showToast()](../../Sources/Register/Camera/RegisterVideoPreviewView.swift#L138-L144) + [RegisterRequiredView.swift showToast()](../../Sources/Register/Required/RegisterRequiredView.swift#L156-L162) + [RegisterBasicInfoView.swift showToast()](../../Sources/Register/BasicInfo/RegisterBasicInfoView.swift#L182-L188)
- **维度**：swiftui-perf / UX
- **产品链路证据**：3 个 view 内的 `showToast` 都用 `Task { @MainActor in try? await Task.sleep(2s); toastMsg = nil }`。若 2s 内触发第 2 次 showToast → 新 toastMsg 覆盖 + 新 Task 排队；**旧 Task 也会跑到 sleep 结束，将新 toastMsg clear 掉**。
- **复查后判定**：**信息**（用户 2s 内连续触发 error 罕见——form validation 都是同步返错，submit isSubmitting guard 拦重复点击）
- **建议**：改用单一 `Task?` 引用，新 showToast 前 cancel 前一个 Task

### P2-3 RegisterAvatarPickerView epoch guard 的 `defer { isAvatarUploading = false }` 无 epoch check

- **文件**：[Sources/Register/BasicInfo/RegisterAvatarPickerView.swift:48](../../Sources/Register/BasicInfo/RegisterAvatarPickerView.swift#L48)
- **维度**：swiftui-perf / UX
- **产品链路证据**：本轮 P1-2 修的 epoch guard 保护了 `store.iconUrl` 不被 stale Task 覆盖；但 `defer { store.isAvatarUploading = false }` **无 epoch check**——慢 Task A 完成时会把当前 running Task B 的 uploading spinner 提前 clear。用户观察：spinner 消失但 iconUrl 还是旧值（B 还在 upload），几百 ms 后 iconUrl 突变到 B。**主要目的（最终 iconUrl 是 B）达成 ✓**，只是过渡态视觉有小 flicker
- **复查后判定**：**信息**（用户主要目的达成；过渡态视觉小 flicker 非阻塞）
- **建议**：`defer { if epoch == store.avatarUploadEpoch { store.isAvatarUploading = false } }`

## 七、正确性核对（关键交互验证）

### 7.1 suspend + deinit + prepare guard 三者衔接

| 场景 | 触发 | 期望 | 实际 |
|---|---|---|---|
| 首次进 record 页 | .task → prepare | state=.idle → 走完 prepare → .ready | ✓ guard case .idle 通过 |
| 录完 push preview | onDisappear → suspend() | session 停 + subscribers 保留 | ✓ camera.stop 派 sessionQueue.async |
| Re-record pop 回 record | onAppear (state==.finished) → restartForRecording | 无条件 camera.start + 3s 轮询 → .ready | ✓ P1-1 修移除 !isRunning guard 后无 race |
| Re-record pop 回后 .task 又触发 | prepare 再次调 | guard case .idle 拦截 return | ✓ prepare 幂等 |
| pop 全栈退出注册流 | @StateObject 释放 → deinit | camera.tearDown() 清 subscribers + stopRunning | ✓ deinit 里 nonisolated 调 tearDown |

**边界**：suspend → sessionQueue.async stop 未跑 + 用户闪电点 Re-record → restartForRecording 无条件 camera.start()（同队 async 排在 stop 后）→ session 状态：stop → start → running ✓
