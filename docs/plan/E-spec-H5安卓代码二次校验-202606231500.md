### 1.0.2 安卓实现的批判性分析（用户明确要求"安卓不一定做得好，你必须判断"）

> 派对房接口参考文档 + IM 常量盘点文档 + `02-04` 三处共同暴露的安卓实现质量问题，iOS 端**不照搬**：

| 安卓问题 | 证据 | iOS 取舍 |
|---|---|---|
| **常量散落 6 处**（NIMMsgAttachType / CustomAttachmentType / PartyBattleAttachType / PartyRoomMsgType / RemoteExtensionType / Const+LiveEventConstant），值有冲突 | IM 常量盘点 §1 总览表 + §9 风险 | iOS 派对房只用**两个** enum：`PartyAttachType: Int`（含 1001/1003/1007/1008/1012/1015/2049 等正数 + -10/-11 表情）+ `PartyMsgType: Int`（公屏渲染分类 0-16，与 attachType 部分映射）。CustomAttachmentType / RemoteExtensionType 留给会话/直播链路用，E 期不引入 |

| **散落魔法数字**：`partyroom/VM.kt:368` 裸 `1100..1112` 判定 PK / `DiamondGiftMsgDispatcher.kt:18` 裸 `1030..1033` 钻石盲盒 / `PartyBattleController.kt:134` 注释 1100~1199 但仅定义到 1112 | IM 常量盘点 §9 风险 | iOS 全部走 enum，禁止范围裸数字；MVP 不接 PK/盲盒/拉新（J），无此风险 |

| **PartyBattle 60s 轮询**死代码：`PartyBattleManager.kt:72-77` `pollJob` 注释 | `04 §3.2` + IM 常量 §9 注释 | E/F 期都不做（NIM 推送驱动，路线图 §2 已锁） |
| **PartyRoomMsgType 与 attachType 部分一一映射部分不映射**：14↔1049、15↔1050、16↔1051 但 0-13 是本地渲染分类无 attachType 直对应 | IM 常量盘点 §6 + 接口参考 §4 | iOS 用两个 enum 解耦：网络层只关心 `PartyAttachType` 数字编码；UI 层用 `PartyMsgType` 决定气泡渲染。两者通过显式映射函数 `attachType → msgType` 转换，**不混为一谈** |

**核心判断**：安卓派对房模块的**业务流程值得照搬**（进房串行 / 麦位对账 / 退房资源释放顺序），但**实现风格不值得照搬**（巨石单例 / 散落常量 / 三套调用方式 / 魔法数字）。iOS 用单一 Swift 风格重写，**值冲突项必须前置与后端对齐**。

### 1.0.3 公共耦合显式标注（用户明确要求"开发时注意公共部分的耦合"）

派对房不复用 `AgoraManager` / `NIMChatroomManager`，但**底层 SDK 与基础设施仍共享**。下表是耦合点清单，implement 期必须按此尺度评估副作用：

| 共享层 | 直播侧持有方 | 派对房侧持有方 | 耦合风险 | 缓解策略 |
|---|---|---|---|---|
| `AgoraRtcEngineKit.sharedEngine(with:)` singleton | `AgoraManager.engine` | `PartyRTCEngine.engine` | sharedEngine 是**进程级单例**，第二次调用复用且忽略新 config（D 期 v5.4 已踩坑），`channelProfile` / `audioScenario` / `delegate` 都需显式 reset | join 前**必须** `setChannelProfile + setAudioScenario + setAudioProfile`；delegate 设置自己；不调 `destroy()`，仅 `leaveChannel` |
| NIMSDK IM 长连接 | `NIMChatroomManager` 触发 `loginManager.login` | `PartyRoomChatManager.enter` 仅 `chatroomManager.enterChatroom`（不再 login） | 多 ChatManagerDelegate 同时挂会被两套都收到 P2P 消息 → 公屏窜消息 | 收消息时**必须**按 `session.sessionType == .chatroom` + 自己的 `roomId` 双过滤 |
| `CryptoUtil`（AES-128-CBC/PKCS7） | `APIClient` | `PartyAPIClient` | 派对房接口若与主接口共用密钥，无新增；若不同套需新增 key/IV | 待后端确认（见 §1.5 #1）；MVP 默认假设共用 dev 主接口密钥 |
| `KeychainStore` token 持久化 | `SessionStore` 存 `loginToken` / `imToken` / `userId` | `PartyAPIClient` 读 `auth_token`（sapi 风格） | sapi `auth_token` 与主接口 `loginToken` **不是同一个**，需 bagshop `exchangeToken` 接口换 | E 期前置承接（原归 I 期"sapi 双 token"基建） |
| `KeychainStore` 单例 | 直播 token | sapi `auth_token` | 同一 Keychain 服务，多字段共存即可 | 字段命名 `auth_token`（与 bagshop 一致），避免与主 token 同名覆盖 |
| `os.Logger` | `AppLogger.*` | `AppLogger.party`（新增 category） | 无 | 新增 category 即可 |
| `LiveStore` / `CallStore` | 直播/通话状态机 | E 期完全不引用 | 0 | 验证：在 PartyStore 头部声明区禁止 `weak var liveStore` / `weak var callStore` |

**后续抽取时机**（用户提示"后续考虑提取公共部分"）：
- **抽取标志**：B/C/D + E 在生产环境跑稳 ≥1 周后，盘点 ≥3 处重复（路线图 §五原则）
- **可抽取候选**：`SharedAgoraEngine`（封装 sharedEngine 单例 + delegate 路由）/ `SharedNIMSession`（封装 login + 多 chatroom 隔离过滤）/ `SapiAuthClient`（auth_token + 401 续）
- **本 spec 不抽**，但在 PartyRTCEngine / PartyRoomChatManager / PartyAPIClient 头部各写一行注释"抽取候选点（路线图 §五）"留口
