## §0 上下文 + 范围

### §0.1 为什么做

Hily iOS 主播端 Profile 模块目前**只读**（`Sources/Profile/ProfileView.swift`），`ProfileHeaderView.swift:79` 编辑铅笔按钮是空 action 占位。H5 主播端资料编辑页早已上线运营（`/profile` 路由），iOS 端缺此功能 → 主播无法自助更新昵称/头像/简介/相册/视频/问候语，只能靠人工介入或删账重建。

**目标**：1:1 复刻 H5 编辑页行为契约，含审核态机制 + 整页单接口提交，让主播在 iOS 端完成全部资料编辑。

### §0.2 范围切分（用户已决策）

**在范围内（7 类可编辑字段）**：

| # | 字段 | API Key | 输入形态 | 审核态 |
|---|---|---|---|---|
| 1 | 昵称 | `nickname` | 单行文本 max 15 字 | ✅ |
| 2 | 头像 | `icon` | 单图上传 max 2MB | ✅ |
| 3 | 简介 | `signature` | 多行文本 max 200 字 | ✅ |
| 4 | 相册照片 | `pics` / `picsDel` | 图片 max 9 张 × 2MB | ❌ |
| 5 | 相册视频 | `videos` / `videosDel` | 视频 max 6 个 × 20MB | ❌ |
| 6 | 来电视频 | `callVideoUrl` / `callVideosDel` | 视频 max 1 个 × 20MB | ❌ |
| 7 | 问候语 | `addGreetList` / `delGreetList` | 每条 max 50 字 · 无数量限制 | ❌ |

**不做（明确排除）**：
- gender / birthday / countryCode / height / bodyWeight —— H5 该编辑页也无这些字段（在其他基础信息页）；iOS 首轮保持一致
- 埋点上报（H5 有 `reportShuShuCustomEvent('h_basic_update', ...)`）→ J 里程碑埋点批次统一做
- 审核结果 push 通知 → 不属编辑页范畴
- 图片裁剪 / 旋转编辑器 → 首轮不做，用户在选图 App 端裁完再选

**推迟到后续里程碑**（backlog）：
- 编辑历史（"上次编辑于 X 天前"）
- 违规字段红色提示（H5 也无）

## §1 业务概念词表

> 词表定义业务语义，不锁 Swift protocol 名。§1a 才落协议命名。

| 词 | 语义 | H5 对照 |
|---|---|---|
| **Draft**（编辑草稿） | 用户当前输入但未提交的字段值集合 | `inputNicknameShow` / `uploadPhoto` 等 |
| **Original Snapshot**（原始快照） | 首次进入编辑页时的服务端字段值（diff 基线） | `profileData.value` |
| **Review Status**（审核态） | 昵称 / 头像 / 简介单字段级"是否处于审核中"标记 | `checkUserDetail.value` |
| **Reviewing Content**（审核中的字段值） | 用户上一次提交但尚未审批的字段值（**不覆盖 draft**） | `checkGreetMsg` |
| **Smart Diff**（智能字段检测） | 提交前逐字段比对 draft vs original，只把变更且非审核中字段塞进请求体 | `handleSubmit` L253-374 |
| **One-shot Submit**（整页提交） | 所有字段一次性 POST 到 `updateUserInfo`（不是每字段独立保存） | 单接口 `/api/user/updateUserInfo` |
| **Field Upload State**（字段上传态） | 单个媒体格独立上传态（idle / uploading / failed） | 无（H5 用全局 `uploading` 标志） |
| **Upload Epoch**（上传轮次守门） | 每次 dismiss / retry 递增的轮次号，stale 异步回调被守 | 无（H5 无此概念） |
| **Greet Message**（问候语） | 主播预设的群发欢迎语，每条 max 50 字 | `greetMsg` |
| **Public Video** vs **Private Video** | 相册/来电视频 acl 公开 vs GiftMessage acl=private | H5 无此区分 |

## §2 H5 / 安卓代码二次校验清单

> **必须前置**（rule `实现纪律铁律`）：spec §3+ 状态机、§4 API 契约、§5 验收清单全部基于本节校验产出的**事实**，不基于 Explore agent 报告的**概括**。

### §2.1 视频上限：**20MB 不是 2MB**（Explore #1 报告有误）

- **图片上限**：`c-uploadImgsAndVideos.vue:31` default 2000 KB → **2 MB**
- **视频上限**：`c-uploadImgsAndVideos.vue:34` default 20000 KB → **20 MB**
- **视频超时**：`c-uploadImgsAndVideos.vue:208` `data.file.type.includes('video') ? 20000 : 10000` → 视频 20s，图片 10s
- **视频扩展名**：`c-uploadImgsAndVideos.vue:369` `['.mp4', '.avi', '.mov', '.wmv', '.flv', '.mkv', '.webm']`
- **图片压缩**：`useOssHooks.js:17-24` maxSizeMB=2 · maxWidthOrHeight=960 · quality=0.7 · minCompressionSize=300KB（小于此不压缩）

**iOS 落地策略**（对齐 rule `legacy-threshold-reeval.md`）：
- 图片 2MB / 视频 20MB：**沿用 H5 硬限值**（前置文件大小校验）
- **视频超时走 iOS 现有 `OssUploadService.videoSession`（60s request / 300s resource，H-2 spec §R-18 已立）**，不用 H5 的 20s。理由：H5 20s 弱网上传 20MB 视频远远不够；iOS 已有 videoSession 基建，直接复用（后续里程碑重估阈值时明示来源，对齐 rule §"在后期里程碑用到已有基础设施时"）
- 视频扩展名：iOS 收窄到 `[.mp4, .mov]`（其他格式 iOS 系统 PhotosPicker 默认不导出，安全默认）
- 图片压缩：`ImageUploader` `.moment` 预设已对齐（960 长边、80% 质量），略优于 H5 → 无需新增 preset

### §2.2 greetMsgs 双结构（**iOS 需扩 model + cache v2 迁移**）

**响应侧**：
| 接口 | 响应字段 | 结构 |
|---|---|---|
| `POST /api/anchor/userInfo` 或 `getMineInfo` | `greetMsgs` | **`[{id: Int, contentDetail: String}]`**（对象数组） |
| `POST /api/anchor/checkUserInfo` | `greetMsgs` | **`[{id: Int, contentDetail: String}]`** 审核中 |

> **注意**：H5 `type.ts:106` 声明 `greetMsgs?: string[]` 是撒谎（对齐 rule `ios-decode-userid-compat.md` 精神——type.ts 不可信）。真实数据结构从 `greetMsgBtn.vue:45` `item.contentDetail` 反推。**Step 1c 起草请求响应 Codable 前必须用真机 raw dump 二次证实**（跑 `ProfileService.getAnchorInfoRaw()` 打印 JSON）。

**请求侧**：
| 请求参数 | 结构 | 用途 |

| `addGreetList` | `[String]`（纯文本数组） | 新增：只传 `contentDetail`，id 由后端生成 |

**iOS 现状**：`Sources/Profile/ProfileModels.swift:39` `let greetMsgs: [String]?` 是**错的**（编辑页无法删除单条）

**变更**：
```swift
struct GreetMsg: Codable, Identifiable, Hashable {
    let id: Int?
    let contentDetail: String?
}
struct AnchorInfo {
    // 原：let greetMsgs: [String]?
    // 改：
    let greetMsgs: [GreetMsg]?

```

**Cache v1 → v2 迁移**（AnchorInfoStore 持久化到 Keychain）：

现状：`Sources/Profile/AnchorInfoStore.swift:48` `cacheKey = "anchorInfoStore.v1"`（当前存 `CachedSnapshot` 嵌套结构含 `info: AnchorInfo?`）

变更策略：
1. **cacheKey 升到 `"anchorInfoStore.v2"`** —— schema 变更必须换 key，否则老 `[String]` 数据 decode 到新 `[GreetMsg]` 会**整个 CachedSnapshot decode 失败** → `try?` 返回 nil → 冷启动闪一次 loading
2. **不做 v1 → v2 数据迁移**（新老共存路径复杂度高、v1 数据无 id 本地无法删问候语，价值低）—— 升 key 后老快照被自然废弃，冷启动走一次 loading + refresh 拿新数据即可
3. **~~AnchorInfo.init(from:) 双兼容 decoder~~ Step 1a 不做**（v2 反悔）—— 属于"防御后端未来偷偷改回 `[String]`"，无产品调用链路证据，符合 rule `code-review-discipline.md` §"顺手做" over-engineering 警告。Auto-synthesized `Codable` 用严格 `[GreetMsg]` decode 即可，老 v1 缓存靠 cacheKey 升级自然废弃。**若 Step 3 真机反悔（后端真返 `[String]` 或字段结构再变），再补双兼容 decoder** 并沉淀 rule
4. **升级后 UX**：老 v1 缓存被 cacheKey 升级废弃 → 冷启动闪一次 loading（约 200-500ms）→ refresh 拿新数据结构。**Step 4 真机验收 N-28** 覆盖冷启动路径

### §2.3 审核态判定源头

**checkUserInfo 响应**（`POST /api/anchor/checkUserInfo`）：
```json
{
  "nickname": string | null,      // 非 null = 昵称审核中
  "signature": string | null,     // 非 null = 简介审核中
  "greetMsgs": [{"id":Int,"contentDetail":String}]  // 非空 = 有问候语审核中
}
```

**头像审核态**从 `POST /api/anchor/userInfo` 响应的 `latestIconAndCallVideo[]` 提取：
```json
{
  "latestIconAndCallVideo": [
    { "businessType": 2, "vaild": 2, "mediaUrl": "..." },  // 头像
    { "businessType": 3, "vaild": 1, "mediaUrl": "..." }   // 来电视频
  ]

```
- `businessType == 2 && vaild == 2` → 头像审核中
- `vaild` 枚举：1 有效 / 2 审核中 / 3 拒绝（对齐 `MediaAsset.vaild` 现有语义）

### §2.4 智能字段检测精确逻辑（H5 `handleSubmit` L253-374 反射）

**判定塞入 requestData 的条件**：
```
if draft.field != original.field AND !review.field:
    requestData[field] = draft.field
```

**媒体字段双数组 diff**（`pics` / `videos` / `callVideosDel`）：
```
pics = draft.photos.filter(new_only).map(url)
picsDel = original.photos
    .filter { p in p.vaild == 3 OR p.id not in draft.photos.serverIds }
    .map(id)
if pics.isEmpty && picsDel.isEmpty: 不塞
```
`vaild==3`（拒绝）原图**强制加入 picsDel**（用户看不到但服务端有，需清）—— H5 L288-293。

**问候语 diff**：
```
addGreetList = draft.greetMsgs.filter { it.serverId == nil }.map(contentDetail)
delGreetList = original.greetMsgs
    .filter { it.id not in draft.greetMsgs.serverIds }
    .map(id)
```

**全空判定**：所有字段都 nil → 返回 `nil` request → 不发接口 → 直接 `dismiss()` 无 toast（对齐 H5 L369-374 `back()`）

### §2.5 上传时机（选图立刻上传，不是点 Confirm 才上传）

- H5 `uploadChangePic` L172-198：选图 → 立刻 `client.put()` → URL 存 `uploadPhoto.value`
- iOS 落地：`PhotosPicker` `onChange(of: selectedItems)` → `Task { await ImageUploader.upload(...) }` → draft.photos append

**优点**：单个失败不阻塞其他字段编辑；Confirm 只发一次接口。
**代价**：用户 dismiss 时若有 uploading 中 → task 需 stale-guard（Upload Epoch）；已上传 URL 不 cleanup（服务端孤儿）—— H5 也一样，acceptable。

### §2.6 UI 审核禁用**如实不统一**（不"统一化"）

**H5 三处禁用 UX 不同**：
| 字段 | 禁用方式 | 用户点击反馈 |
|---|---|---|
| 昵称 | `showEditNickname` 弹窗前拦截 → toast | ✅ 有 toast |
| 头像 | 上传按钮包 `<div v-if="!checkUserDetail.icon">`（点击**无反馈**） | ❌ 无 toast（H5 也这样） |
| 简介 | `<van-field :disabled="checkUserDetail.signature">` | ❌ 无 toast（disabled 天然不可编辑） |

**iOS 落地**：
- **昵称**：铅笔按钮 action 内分流（`if isReviewing { showToast(...) } else { showSheet() }`）——不用 `.disabled`
- **头像**：**审核态用条件分支渲染**——不同 view 树，不用 overlay 拦截（v1 错设计，v2 修正）：
```
if isReviewing {
    Button { toast("Sorry, your profile detail is in review") } label: { AvatarImage(url: ...).overlay(InReviewBadge(.overlay)) }
} else {
    PhotosPicker(selection: ..., matching: .images) { AvatarImage(url: ...) }
}
```
理由：PhotosPicker 内部把整个 label 转成系统按钮，上面盖 `.onTapGesture` 手势不会 win（SwiftUI hit test 优先级问题，对齐 rule `swiftui-button-plain-hitarea.md`）—— **v1 spec 用 overlay 是错的**
- **简介**：TextEditor `.disabled(isReviewing)` 天然不可编辑，**无 toast**（H5 一致，rule 精神——不"统一化"）

### §2.7 保存成功后行为

**H5 L388-400**：
1. 弹 `useStandardPopup({ title: "Submitted for approval, please wait...", confirmText: "Confirm" })`
2. 用户点 Confirm → `router.back()`
3. **不刷新数据**（H5 依赖 Profile 页 `onActivated` 自动刷）

**iOS 落地**：
1. 用 SwiftUI `.alert(title, isPresented:)` 单 Confirm 按钮弹窗
2. 用户点 Confirm → `Task { await AnchorInfoStore.shared.refresh(); dismiss() }`
3. `refresh()` 内自动清 image cache（`AnchorInfoStore:104-114`），保证 Profile 页头像/相册立即刷新
4. **不做 optimistic update**（禁止直写 store.info；打破单向数据流）

## §3 状态机

### §3.1 页面级 Phase

```
                          .loadError ──Retry──┐
                              ▲               │
loading ──成功──▶ editing ────┴───────────────┘
                     │
                     ├─(field-level: idle → uploading → idle/failed)
                     │
                     ├─Confirm(有变更)───▶ saving ──成功──▶ success ──Confirm──▶ dismiss
                     │                        │
                     │                        └─失败(API/网络)──▶ editing + toast
                     │
                     └─Confirm(无变更)───▶ dismiss(不发接口)
```

**Phase 枚举**（Swift 待 §1a 定型）：
```
enum Phase: Equatable {
    case loading
    case editing
    case saving
    case success        // 弹 dialog，Confirm 后 refresh + dismiss
    case loadError(String)
    case terminated     // 挤下线/token 失效 → view 立即 pop，不弹 alert
}
```

**`.terminated` 触发**：`SessionStore` 的 `.apiSessionInvalidated` 通知 observer 命中时，任何 phase 都强制转 `.terminated` → view 层 dismiss（不弹 success alert 即使刚刚 saving 成功）。

### §3.2 Field-level 上传子态（每 tile 独立）

```
    ┌─────┐  选图    ┌───────────┐  成功  ┌─────┐
    │idle │────────▶ │uploading  │─────▶│idle │
    └─────┘         └───────────┘       └─────┘
       ▲                 │
       │                 │失败
       │重试             ▼
       └────────────┐  ┌────────┐
                    │◀─│ failed │
                    │  └────────┘
                    │删除tile
                    └────▶(remove from draft)
```

**FieldUploadState**（每 `DraftMediaItem` 内嵌）：
```
enum FieldUploadState: Equatable {
    case idle
    case uploading(localId: String)   // localId 用于 stale callback 守卫
    case failed(msg: String)
}
```

**Upload Epoch 守卫**：`store.uploadEpoch: Int` 每次 dismiss / cross-field batch retry 时 `+= 1`；每个上传 task 启动时 capture 值，完成时 `guard epoch == self.uploadEpoch else return`。

### §3.3 非法转移守护

| 非法转移 | 场景 | 守护策略 |
|---|---|---|
| `.loading → .editing` 但 review 数据缺 | checkUserInfo / userInfo 任一失败 | 转 `.loadError` 整页 retry |
| `.editing → .saving` 但有 uploading tile | 用户点 Confirm 时抢跑 | `handleConfirm` 入口 assert；不满足 → toast + 保持 `.editing` |
| `.saving → .editing` 后异常回调 | updateUserInfo 请求还在飞 但 view 已被 pop | Task cancel + Upload Epoch |
| Field: `.failed → .uploading` 但用户已删 tile | 用户点 retry 前又点 × | 删除时先 cancel task；retry 按 tile 存在性 guard |
| Field: `.uploading → .uploading` 覆盖上传 | 用户点 tile → 立即再选另一张换图 | 前一个 upload task cancel（`task.cancel()`）+ Upload Epoch 递增 → 老 task 完成时 guard 丢弃结果 |
| Any → `.terminated` | `.apiSessionInvalidated` 通知触发 | 观察者立即置 phase = `.terminated`，view 层 dismiss；saving 阶段不再弹 success alert |
| ScenePhase `.active → .background` 期间有 uploading | 用户切后台超时 | store 记录 `enteredBackgroundAt`；回前台若 `.uploading > 60s`，主动标 `.failed(.systemSuspended)`（URLSession 后台被系统挂起，避免 stuck） |
| ScenePhase `.background` 时 `.saving` 中请求完成 | 后台完成回调触发 phase 转 `.success` | phase 转成但不弹 alert；view 层 `.onChange(of: scenePhase)` 回 `.active` 时再展示 alert |

### §3.4 Draft State（完整数据 shape）

```
struct DraftState: Equatable {
    var nickname: String
    var avatarUrl: String                    // 已上传的 CDN URL
    var signature: String
    var photos: [DraftMediaItem]             // 有 serverId 者为原图；nil 者为新增
    var videos: [DraftMediaItem]
    var callVideo: DraftMediaItem?
    var greetMsgs: [DraftGreetMsg]           // 含原有 + 新增，删除 = 从数组移除
}
struct DraftMediaItem: Identifiable, Equatable {
    let id: String                           // "asset-<serverId>" or "local-<uuid>"
    let serverId: Int?                       // 非 nil = 原图
    var url: String                          // 上传后 CDN URL 或原有 URL
    var coverUrl: String?                    // 视频封面
    var uploadState: FieldUploadState
}
struct DraftGreetMsg: Identifiable, Equatable {
    let id: String
    let serverId: Int?                       // 非 nil = 原有
    var content: String
}
```

**Original Snapshot**：`store.originalSnapshot: OriginalSnapshot` —— loading 完成后写一次，此后不再改（对齐 H5 `profileData.value`）。

## §4 API 契约

> 全部走现有 `APIClient` / `PartyAPIClient`。主接口用 **APIClient**（Profile 属于主接口范畴）。

### §4.1 GET/POST 五个接口（追字面 path，对齐 rule `api-http-method-strict.md`）

| # | 用途 | Method | 字面 path | H5 调用点 / iOS 现有 |
|---|---|---|---|---|
| 1 | 拉审核中字段 | **POST** | `/api/anchor/checkUserInfo` | index.vue:108（iOS 侧 EditProfileService 新写） |
| 2 | 拉完整用户信息 | **POST** | `/api/anchor/userInfo` | user.js:92 `getAnchorInfo()`（iOS 侧 `ProfileService.getAnchorInfo()` 现有；本页需要 `latestIconAndCallVideo`/`picList` 字段扩展或补 `getFullUserInfo` 姊妹方法） |
| 3 | 保存核心接口 | **POST** | `/api/user/updateUserInfo` | index.vue:376（iOS 侧 EditProfileService 新写） |
| 4 | OSS 凭证 | **POST** | **`/sts/getOssUploadParam`**（**无 `/api/` 前缀**，iOS 侧已有） | `OssCredentialService.getOssUploadParam()`（`Sources/Core/Upload/OssCredentialService.swift:19`） |

**关键校验**（对齐 rule `api-http-method-strict.md`）：
- **接口 4 iOS 侧 endpoint 与 H5 不同**：H5 用 `/sts/getkey`（ali-oss SDK 兼容），iOS 走主接口加密通道 `/sts/getOssUploadParam` 返 `OssCredential`（已封装）。**不复用 H5 endpoint**，直接用 iOS 现有 `OssCredentialService.shared`（v1 spec 错写为 `/sts/getkey`，v2 修正）
- 接口 3 是真正核心，其他都是辅助
- 视频上传 iOS 侧需**新建 `PublicVideoUploader.swift`**（Sources/Core/Upload/）——不扩现有 `OssUploadService.uploadVideo` 的 acl 参数（现有硬编 `acl=private` 是 GiftMessage 契约，扩参数破坏其调用点）

#### 4.2.3 `/api/user/updateUserInfo` 请求

> **id 类型策略**（对齐 rule `ios-decode-userid-compat.md`）：本 spec **不锁 `Int` 或 `String`**。Step 1c 起草请求 model 前必须**真机抓包**证实后端接收 id 时是 Int 还是 String（H5 `findMissingIds` 不做类型转换，透传服务端原生类型 → 网关可能自动 stringify）。抓包结论确定后二选一：
> - 若后端接收 `Int`：`picsDel: [Int]?` 编码即可
> - 若后端接收 `String`：`picsDel: [String]?`，或走 `[EitherStringOrInt]` 双兼容 encode

```swift
struct UpdateUserInfoRequest: Encodable {
    var icon: String?
    var nickname: String?
    var signature: String?
    var pics: [String]?              // 新增照片 URL
    var picsDel: [ID_TYPE]?          // 删除照片 ID（类型 Step 1c 抓包定）
    var videos: [String]?
    var videosDel: [ID_TYPE]?
    var callVideoUrl: String?
    var callVideosDel: [ID_TYPE]?
    var addGreetList: [String]?
    var delGreetList: [ID_TYPE]?
}
// typealias ID_TYPE = String  或  Int  —— Step 1c 抓包后 pin 定
```

#### 4.2.4 响应类型

`updateUserInfo` 成功响应体是空（H5 L385 不用返回值），iOS 侧 `APIClient.post` 无 typed response 时用 `.postVoid` 或 `.post<EmptyResponse>`。

### §4.3 错误码分流

| Code | 场景 | iOS 处理 |
|---|---|---|
| `0000` | 成功 | 走 `.success` phase |
| `1004` | 挤下线 | 全局 `apiSessionInvalidated` 通知已处理，本页无需特殊 |
| `1005` | Token 失效 | 同上 |
| `1080` | 保留（余额相关，本页不涉及） | 忽略 |
| `2001`/`1992`/`1006` | 直播权限（本页不涉及） | 忽略 |
| 其他 | 业务错误 | catch APIError → view 层 toast 显示 `error.message` |

**OSS 上传错误**：
- 网络超时 → 视频 20s / 图片 10s（Step 1c 真机跑长视频验证 timeout 触发行为）
- 单个上传失败 → tile 状态转 `.failed(msg)` + 显示重试按钮；不阻塞其他 tile
- 部分成功 → Confirm 按钮 disable + toast "Some uploads failed, please retry"

## §6B 潜在坑（Step 3 真集成前必读）

### 6B.1 视频 acl 语义分歧
`OssUploadService.uploadVideo` 硬编 `acl=private`（GiftMessage 专用私密媒体）。EditProfile 视频公开可见——**新建 `PublicVideoUploader.swift`（Sources/Core/Upload/）姊妹方法**（不扩现有 `uploadVideo` 的 acl 参数，避免破坏 GiftMessage 调用点）。新 uploader 一站式风格对齐 `ImageUploader`：拿凭证 + 校验扩展名/大小 + `OssUploadService.performUpload(objectAcl: nil, useVideoSession: true)`。

### 6B.2 SwiftUI PhotosPicker 审核态用**条件分支**而非 overlay
审核态禁用**不能**用 `.disabled` + PhotosPicker（会屏蔽点击 = 屏蔽 toast）；也**不能**用透明覆盖层 + `.onTapGesture`（PhotosPicker 内部把 label 转成系统按钮，hit test 优先级高于覆盖层 → 覆盖手势不 win）。**正解**：条件分支渲染两条不同 view 树：
```
if isReviewing {
    Button { toast("Sorry, your profile detail is in review") } label: { ... }
} else {
    PhotosPicker(selection: ...) { ... }
}
```
对齐 rule `swiftui-button-plain-hitarea.md`。**验收 N-2** 覆盖此坑。**v1 spec 用 overlay 是错的，v2 修正**。

### 6B.3 refresh 完成前 pop 会显示旧头像
Confirm 点击 → alert 期间 `await AnchorInfoStore.refresh()` 完毕后再 dismiss（避免闪烁）。alert Confirm 按钮加 loading spinner 避免"卡住"误感（可选）。**验收 P-10** 覆盖。

### 6B.4 Cache v2 migration 破坏老用户体验
`AnchorInfoStore` 从 Keychain decode v1 数据（`greetMsgs: [String]?`）需要 wrap 成 `[GreetMsg(id: nil, ...)]`。**关键**：v1 数据无 id → 本地无法删除已存在的问候语，需下次 `refresh()` 后拿新 id → 用户体验：**升级后首次进编辑页删除问候语，需先下拉刷新 Profile 一次**。可接受，但需 spec §5 N-28 单测覆盖。

### 6B.5 视频超时已由现有 `videoSession` 60s 覆盖
iOS `OssUploadService.videoSession`（`OssUploadService.swift:34-42`）已配 `timeoutIntervalForRequest = 60` / `timeoutIntervalForResource = 300`（H-2 spec §R-18 立的，明确高于 H5 20s）。EditProfile 视频路径**必须走 videoSession**（`PublicVideoUploader.upload` 内传 `useVideoSession: true`），不用 H5 的 20s。**v1 spec 说"沿用 H5 20s"是错的，v2 修正**（对齐 rule `legacy-threshold-reeval.md` §"在后期里程碑用到已有基础设施时"）。

### 6B.6 相册视频封面 coverUrl 从哪来
H5 上传视频后**服务端异步生成封面**，picList 里返回 `coverUrl`。iOS 编辑页新上传视频 draft 阶段 `coverUrl = nil` —— 用系统 AVAsset 前 1 秒帧作为本地封面占位。**验收 P-6** 需含此 case。

### 6B.7 SwiftUI Sheet + PhotosPicker 生命周期
昵称编辑用 `.sheet(item:)` 弹窗内**无** PhotosPicker（只 TextField）→ 无此坑。头像/相册 PhotosPicker 在主页 inline → 无此坑。对齐 rule `swiftui-fullscreencover-hoist.md` 精神。
