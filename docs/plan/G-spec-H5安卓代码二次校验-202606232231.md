## 1.2 冲突项（已决策）

| 维度 | 决策 | 理由 |
|---|---|---|
| 多频道 SDK 模式（H5 多 client vs 安卓 joinChannelEx） | **iOS 走安卓 `joinChannelEx + AgoraRtcConnection 字典`** | H5 多 client 是 Web SDK 限制（agora-rtc-sdk-ng 无 joinChannelEx）；iOS 4.5.2.9 BASIC 支持 joinChannelEx，单 engine 多连接性能/资源更优；token 复用同 rtcToken。安卓 02-03:57 `LivePkManager.joinChannelEx` 为权威实现 |
| 多频道 codec（H5 vp9 vs iOS h264） | **R1 中高风险，M0 阶段独立验证 iOS h264 ↔ H5 vp9 同频道互通**；**不显式配置 codec**，沿用 SDK 4.5.2.9 BASIC 默认（编 h264 / 解 vp8/vp9/h264 兼容） | 当前直播+通话**完全未配置 codec**（`AgoraVideoEncoderConfiguration` 无该字段），靠 SDK 自动协商；声网官方声明 vp9↔h264 互通但工程零实证；M0 提测点 4 项含"iOS 主播 + H5 vp9 主播同频道双向看画面"。失败时回退方案：A 后端协调 H5 改 h264；B 私有键 `setParameters("{\"che.video.h264_profile_main\":true}")` 强制；C 服务端转码（详见 §1.4 R1） |
| **PK 期编码档位降级** | 未提 | **新增 `.pkActive` 档位：480×640 / 30fps / 500kbps**，PK 期 `joinPKOpposite` 成功后立即应用；exit endingPK 回 `.normal` | PK 容器 ≈ 屏宽一半（iPhone 标准 197pt @3x ≈ 591px），推 720 宽是浪费；30fps 保留 PK 顺滑感；500kbps 比 Standard 砍半，双频道总带宽预算节省 ~50%，缓解 R4 拥塞风险。弱网叠加：PK 期间若 NetworkQualityMonitor 触发 `.low`，按 `max(.pkActive, .low)` 取更激进档位（即降到 480×640/15fps/400kbps） |
| `pkStatus` 注释 vs 代码冲突 | **信代码**：7=客态进入 PK / 8=PK 结束进惩罚 / 9=对方结束惩罚或中断 / 10=匹配成功 / -1=对方异常断线 | `constant/livePk.ts:13-23` 注释陈旧；以 `live.js:604` switch case + 安卓 02-03:72 为准（双端一致） |
| 接口端点数（路线图 13 vs H5 17） | **G 必用 9 个全实现**：startPkMatch / cancelMatch / joinPk / invitePk / handleInvite / endPk / endPunishing / getPkTop3RankList / getPkStatus / mutePkRoom（共 10 个）；其余 7 个 G 范围外仅 `PKService` 留签名占位（getRecommendAnchorList / getPkRankList / getPkRecordList / queryInviteSwitch / updateInviteSwitch / getPkInfo / selectPKRuleIcon） | G 范围收窄（极简入口 + 不做客态 + 不做推荐列表/历史/规则 UI）后，必用接口降到 10 个；占位接口保留方法签名便于 H/I 接续 |
| 邀请开关 PK 期处理（H5 未显式做） | **enter inPK 时 POST /updateInviteSwitch(off) + 快照原始值；exit endingPK 时按快照恢复** | H5 依赖 `callState !== 0` 天然挡，但 iOS 必须显式调以避免 D 来电脏跳（详见 §1.4 R5）。快照恢复防覆盖用户主动关闭状态（决策 R6） |
| PK 与 D 私 call 互斥 | **`CallStore.handleIncomingVideoCall` 显式插入 PKStore 检查分支 → busy reject**；不依赖现有 `callState == 0` 隐式守卫 | iOS 现状 `Sources/Call/CallStore.swift:652` 守卫 `callState == 0` 在 PK 期（callState=3）fall through 到 line 657 idle 检查后**会创建错通话**；安卓事件驱动天然互斥不适用 iOS 调用栈，必须显式补 |
| 客态 PK | **G 范围外**（spec backlog 留位） | 客态依赖"主播浏览他人房间"链路，工程内未实现；做完整客态等于"一次做两件新事"，风险叠加。客态延到该链路落地后单独 spec |

## 1.5 风险登记（编号沿用规划文 §八）

- **R1** H5 主播 vp9 + iOS h264 同频道互通：**风险等级中高**（项目内 codec 完全未配置过、零实证）；M0 阶段独立真机验证；失败时回退方案 A 后端协调 H5 改 h264 / B 私有键 `setParameters` 强制 / C 服务端转码（详见 §1.2）
- **R2** NIM attachType -8/-9 推送形态（Int 负数 vs String "-8"/"-9"）：M1 单测覆盖两路径 + 后端口头确认
- **R3** endTime 时间戳单位（毫秒 vs 秒）：**M1** 联调时 1 分钟内确认（与 PKService.joinPk decode 同步，避免 M2 PKCountdownController 用错单位后 M3 真机才暴露）
- **R4** PK 期双频道码率/带宽拥塞：M0 起即应用 `.pkActive` 档位（480×640/30fps/500kbps，比 .normal Standard 砍半），主动从源头压预算；M7 真机弱网专项叠加验证
- **R5** PK 期 D 私 call 旧守卫 fall through 创建错通话：已识别，M6 显式插入 PKStore 检查
- **R6** invite switch 快照恢复并发竞态（用户 PK 中手动切开关）：enter 时快照 + exit 时复检最新值再决定是否恢复
- **R7** H5 `constant/livePk.ts` 注释与代码不一致（pkStatus=7/10）：规则"信代码"，已锁定
- **R8** getPkStatus 返回字符串无法重建杀进程后的 PKContext（pkId/oppositeUid/oppositeChannel/endTime）：M1 与后端协调方案 A 扩 getPkStatus / 方案 B 新增 getPkDetail / 方案 C 本地缓存 ctx（详见 spec §7.2）
- **R9** `setVideoEncoderConfiguration` 是 engine 级别，PK 期切 `.pkActive` 同时影响主频道观众端画质：接受此行为（双频道带宽下降）；M0 真机观众端肉眼评估；若产品不可接受调研 connection-level 编码 API
- **R10** `renewToken` 在多 connection 下是否自动覆盖所有 connection：M0-3 真机长跑（≥1h）验证；失败改逐 connection `renewTokenEx`
- **R11** updateInviteSwitch 接口幂等性：M1 与后端确认连续两次同值是否安全；不幂等则 PKStore 加状态机记录避免重复写
