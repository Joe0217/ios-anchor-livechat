## 二、建议

### 建议-1 performReload 里的 `Task.detached { @MainActor [self] in ... }` 注释理由不成立

- 文件：[Sources/Profile/AnchorInfoStore.swift:140-156](../../Sources/Profile/AnchorInfoStore.swift#L140-L156)
- 维度：Swift 并发（文档准确性）
- **复查后判定**：**建议**（本次会话改过 performReload 但沿用了既有的 `Task.detached` 写法，注释可顺手订正）
- 触发场景：**运行时无影响**，仅是**文档措辞误导后续维护者**
- 证据链：
  - `Task.detached { @MainActor [self] in ... }` 立即 hop 回 MainActor，等于抵消了 detached 的"不继承 actor"效果
  - 与 `Task { @MainActor in ... }` 在 @MainActor 类内**完全等价**（都是 unstructured Task，都不继承 view `.task` 的 cancel token）
  - 真正实现"请求脱离 view cancel"的是 **unstructured Task**（无论 detached 与否），不是 detached 本身
- 修复（二选一）：
  - **保留代码不动**（因为行为正确），把注释改为 "用 unstructured Task 让请求脱离 view .task 的取消传播"
  - 或简化为 `Task { [weak self] in guard let self else { return }; await self.doReload(epoch: epoch) }`
- 优先级：因本次会话是加 epoch guard 顺手接入，可与必修-1 一起修

## 六、方法论说明

**为什么大量 finding 被判"范围外"**：
用户明确"仅审查当前会话的所有改动"—— finder 是按整文件跑的，会把文件里所有可疑点都报出来。二次复查按 `git diff HEAD` + 记忆核对**本次会话真正新增的行**，只留下与本次改动直接相关的问题。

**为什么"信息级 3 票对抗"不能替代主流程二次复查**：
按 [code-review-discipline.md §7](../../.claude/rules/code-review-discipline.md)，Workflow 内 3 票对抗是 finder agent 互投，**不等于**实际产品调用链证据 —— 本次误报剔除的 5 项就是明例（3 票都通过但主流程 grep 场景后确认误判）。

**下次同类审查如何缩短耗时**：
- 若只想审本次改动，先跑 `git diff HEAD -- Sources/**/*.swift` 拿精确文件清单，避免 finder 扫描无关行
- 复查阶段可 skip "非本次改动的行"，聚焦新增/修改的行号做产品调用链核对
