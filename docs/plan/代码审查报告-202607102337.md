## 二、P0（必修）

### P0-1 IM attachType 52 缺字段/空串兜底 open=true 与 H5 语义相反，破坏"关闭私 call"修复目标

- **文件**：[Sources/Live/NIM/SystemMessageRouteDecision.swift:117-135](../../Sources/Live/NIM/SystemMessageRouteDecision.swift#L117)
- **维度**：correctness / H5 契约对齐
- **复查后判定**：必修（有明确产品调用链路证据）

**风险**：

iOS 侧 `.privateCallSwitchChange` 解析当 `privateCallOpen` 字段缺失或为空串时**兜底返回 `open=true`**，会 emit `.privateCallSwitchChange(open: true)` 强制把 `LiveStore.privateCallOpen` 覆写为 `true`。

对比 H5 [stores/modules/live.js:306-307](../../../anchor-livechat-h5/src/stores/modules/live.js#L306)：

```javascript
if (ext?.attachType === 52 && ext?.data?.privateCallOpen !== '')
  this.currentLiveInfo.privateCallOpen = ext?.data?.privateCallOpen
```

H5 显式 guard `!== ''`：**只在明确有值时更新**，`undefined` / `null` / `''` 一律跳过（不改本地）。

**触发场景**（有产品调用证据）：

1. 主播 toggle → 关闭 → `LiveStore.privateCallOpen = false` ✓
2. 后端因其它业务原因广播一条 attachType=52 的消息，但 `data.privateCallOpen` 为空串或缺失（H5 显式防御此 case 证明后端确实存在这种 payload）
3. iOS `SystemMessageRouteDecision.decide` 返回 `.privateCallSwitchChange(open: true)`
4. `SystemMessageRouter` execute case 调 `liveStore?.setPrivateCallOpen(true)` → LiveStore.privateCallOpen 被误设为 `true`
5. `CallStore.handleIncomingVideoCall` 收到私 call → guard 通过 → 走 `pauseForCall` 自动接听
6. **主播明明关了却又能被拨入 → 本次会话主要修复目标破功**

**修复**：

payload 无有效值时应返回 `.passThrough`（保持 store 现值不变），对齐 H5 空串跳过语义：

```swift
case .privateCallSwitchChange:
    let raw: Any? = {
        if let d = payload["data"] as? [String: Any] { return d["privateCallOpen"] }
        return payload["privateCallOpen"]
    }()
    // 对齐 H5 live.js:306 `!== ''`：无值/空串跳过，不覆盖本地
    guard let raw else { return .passThrough }
    if let s = raw as? String, s.isEmpty { return .passThrough }
    let open: Bool = {
        if let n = raw as? Int { return n != 0 }
        if let n = raw as? NSNumber { return n.intValue != 0 }
        if let s = raw as? String { return Int(s) != 0 }
        return true   // 只有 Bool/其他不识别类型才走 true（极小概率）
    }()
    return .privateCallSwitchChange(open: open)
```

**关联影响**（同 commit 需一并修）：

[Tests/HilyTests/SystemMessageRouterTests.swift:230-234](../../Tests/HilyTests/SystemMessageRouterTests.swift#L230) 的 `test_privateCallSwitchChange_missingField_defaultOpen` 断言当前会被打破：

```swift
XCTAssertEqual(decide(.privateCallSwitchChange),
               .privateCallSwitchChange(open: true))
```

应改为断言 `.passThrough`（更符合 H5 语义），或用 `test_privateCallSwitchChange_missingField_passThrough` 重命名。

同款：`test_privateCallSwitchChange_stringValue` 若传空串 `["privateCallOpen": ""]` 也应断言 `.passThrough`（当前用 `"0"` 传入未命中该分支，但可补一条空串 case 加固）。

## 三、P1（建议）

### P1-1 handlePrivateCallToggle 失败 toast 复用 "coming soon" 文案，与"网络失败请重试"语义不符

- **文件**：[Sources/Live/LiveRoomView.swift:699,711](../../Sources/Live/LiveRoomView.swift#L699)
- **维度**：i18n / UX
- **复查后判定**：建议（有触发路径但影响仅限文案理解，非功能性）

**风险**：

`handlePrivateCallToggle` 里两处失败分支（roomInfo.id 缺失、API 失败）都复用 `L10n.liveRoomComingSoonPrivateCall` 作为 toast。该 key 在 [L10n.swift:853](../../Sources/L10n.swift#L853) 的注释是"点击 Private Call 大按钮占位提示"，英文文案是 `"Private call coming soon"`（见 [en.lproj/Localizable.strings:415](../../Sources/en.lproj/Localizable.strings#L415)）。

**触发场景**：任一次 updatePrivateCall API 失败（网络抖动、后端 500、DNS 抖动）都会命中；用户看到 "Private call coming soon" 会误以为"功能未开放"而不是"临时失败请重试"。

对比 H5 [liveRoom.vue:375](../../../anchor-livechat-h5/src/views/liveSetting/components/liveRoom.vue#L375)：`showToast('Private call switch failed, please try again.')`。

**修复**：新增 L10n key（三语言 EN/AR/TR）：

```
"liveRoom.privateCall.switchFailed" = "Private call switch failed, please try again.";
```

`handlePrivateCallToggle` 两处 toast 改用新 key。

### P2-2 handlePrivateCallToggle 无 in-flight 防抖 —— 快速连续 toggle 有 race

- **文件**：[Sources/Live/LiveRoomView.swift:695-716](../../Sources/Live/LiveRoomView.swift#L695)

- **复查后判定**：信息（H5 同款、影响面小）

**建议**：暂不修（对齐 H5）。若产品验收报"闪速点开关状态混乱"，加个 `isInFlight` guard。

### P2-3 iOS updatePrivateCall 端点去掉 H5 字面尾部空格 —— 真机验收环节

- **文件**：[Sources/Live/LiveService.swift:167](../../Sources/Live/LiveService.swift#L167)

- **复查后判定**：信息（已在注释注明，真机验证会暴露）
